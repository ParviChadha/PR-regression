# Pull request #5800: Report one-character non-numeric array indices like longer ones

## Description
Two low-priority findings from a standards-conformance read-through of the library.

## JSON pointer: same error for `/a/x` and `/a/xy`

When a JSON pointer indexes into an array, each reference token must be a number. Before this change, a non-numeric token was reported differently depending only on its length:

| Token | Before | After |
|---|---|---|
| `/a/xy` | `parse_error.109` "array index 'xy' is not a number" | unchanged |
| `/a/x` | `out_of_range.404` "unresolved reference token 'x'" | `parse_error.109` "array index 'x' is not a number" |
| `/a/-` | `out_of_range.404` | unchanged |
| `/a/` (empty token) | `out_of_range.404` | unchanged |

The cause is that `parse_array_index` only ran the "begins with a digit" check for tokens longer than one character (since v3.8.0, bfc003cad). The check now covers one-character tokens too. It leaves out `-`, which RFC 6901 defines as "past the end of the array" (`patch.md`/`patch_inplace.md` document 404 for removing it), and the empty token.

The `unflatten.md` example for 404 used `'x'`, so it now uses `'-'`, and the wording names the cases that still give 404.

Docs: the version history of `at`, `operator[]`, `value`, `patch`, `patch_inplace`, and `unflatten` now records the change for 3.13.0. `exceptions.md` says which array indices throw `parse_error.109` and which `out_of_range.404`, and notes the pre-3.13.0 behavior.

## `ordered_map::erase`: comment only

`erase(first, last)` destroys a `std::pair<const Key, T>` and placement-news a new one in the same storage. Before C++20, `[basic.life]/8` did not count such a new object (its type has a const member) as transparently replacing the old one, so access through the vector's existing pointers was formally UB without `std::launder`. `std::launder` doesn't exist before C++17 anyway. C++20 dropped that condition (P1971R0, NB comment US 041), and compilers have always treated the pattern as intended. A comment now records this; the code is unchanged.

## Public API

No signatures change and the ABI is unaffected, but there are behavior changes, **only for one-character array reference tokens that are neither a digit nor `-`**:

- `at()`, `operator[]`, `patch()`/`patch_inplace()`, and `unflatten()` throw `parse_error.109` instead of `out_of_range.404`. Code that catches `json::out_of_range` for this case stops catching it; catching `json::exception` still works.
- `value(json_pointer, default)` on an array with such a token used to return the default and now throws `parse_error.109`, as it already did for longer tokens like `/foo`.
- `contains()` does not change; it still returns `false`.

The `ordered_map` change is a comment only and breaks nothing.

## Tests

- `unit-json_pointer.cpp`: `/x` and `/+` with `operator[]`/`at()` (const and non-const), `contains()`, and `unflatten()`; `-` in `unflatten()` still gives 404.
- `unit-element_access2.cpp`: `value("/x", default)` throws 109.
- `unit-json_patch.cpp`: `remove` of `/a/-` (404), `/a/x`, and `/a/xy` (both 109).

I ran these locally in C++11/17/20, with `JSON_DIAGNOSTICS` and with `JSON_DIAGNOSTIC_POSITIONS`, together with `unit-alt-string`, `unit-disabled_exceptions`, `unit-ordered_map`, and `unit-ordered_json`.
