# Pull request #5927: Skip CBOR tags in front of map keys, validate indefinite text chunks, fix CBOR docs

## Description
## Summary
- `from_cbor` with `cbor_tag_handler_t::ignore` or `store` now skips tags in front of a text string map key, as it already did in front of values. Before, `A1 C0 61 61 0A` threw `parse_error.113 … found a tag`. SAX behaves the same. The `error` handler is unchanged.
- The chunks of an indefinite-length text string are now UTF-8 checked individually (RFC 8949 §3.2.3). Before, they were concatenated and checked once, so a split code point or an invalid chunk was accepted under `strict`, and `replace`/`ignore` gave different results.
- Docs: corrected the negative-integer rows, the 0x1B row, the F9/NaN history (NaN/Inf were already `F9` before 3.13.0, since 3.8.0), the tag/subtype description and the `StringType`/`BinaryType` requirements; added the "not deterministic encoding" note (RFC 8949 §4.2), duplicate keys (§5.3.1), the tag-key and per-chunk rules, the complete exception list of `from_cbor`, the pointer/C-array input trap and the partial-output note.
- Tests added to `unit-cbor.cpp` (incl. a 100000-tag chain, SAX, exact messages).

## Breaking changes
No API or ABI change. Behaviour:
- `ignore`/`store`: input with a tag before a text string key was an error and is now accepted.
- `strict`/`replace`/`ignore`: an indefinite-length text string whose chunk is not valid UTF-8 on its own (including a split code point) is now rejected (`parse_error.113`) or sanitized per chunk. This is input RFC 8949 declares invalid. `keep` (default) is unchanged; conforming input is unaffected.
- No new requirement on `StringType`/`BinaryType`.

Verified with cbor2 and against RFC 8949; reviewed independently before submission.

* Skip CBOR tags in front of map keys and validate indefinite text chunks

A tag in front of a text string map key was rejected with parse_error.113
even with cbor_tag_handler_t::ignore or store, although tags in front of
values are handled. The tags are now skipped iteratively before the key is
read; the handler error still rejects them.

the single UTF-8 check, so a code point split over two chunks, or an
invalid chunk, was accepted. RFC 8949, Section 3.2.3 requires every chunk
to be valid on its own. With error_handler_t::strict, replace and ignore
each chunk is now checked; keep is unchanged. The chunks are appended with
append(ptr, len), so StringType needs nothing new.
