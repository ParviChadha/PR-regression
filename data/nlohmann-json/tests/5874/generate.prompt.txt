# Pull request #5874: Read FILE* input with std::fgetc under MemorySanitizer

## Description
Since #5828, `file_input_adapter::get_character()` reads with `getc_unlocked` where the C library has it. With glibc and optimization (`-O1` and up), `<stdio.h>` makes `getc_unlocked` an extern inline function that reads the stdio buffer (`fp->_IO_read_ptr`) directly. glibc filled that buffer, and glibc is not instrumented, so MemorySanitizer treats the bytes as uninitialized and reports a false positive when a parser reads from a `FILE*`. The bytes are in fact initialized.

OSS-Fuzz issue 575915982 (`parse_bson_fuzzer`, job `libfuzzer_msan_json`, input `20 20 20 20 20`) hits this through the `fmemopen` leg of `check_input_adapters()` (#5827). `std::fgetc` is an opaque library call, and MemorySanitizer treats its result as initialized.

This PR selects `JSON_UNLOCKED_FILE_IO 0` (plain `std::fgetc`) when `__has_feature(memory_sanitizer)` is true. The docs of `JSON_DISABLE_UNLOCKED_FILE_IO` now say so.

The regression came in with #5828 (merged 2026-10-19) and is not part of any release.

### Testing

- Reproduced with clang 18 and an MSan-instrumented libc++ 18.1.3: without this change the OSS-Fuzz testcase reports `use-of-uninitialized-value` (origin: glibc's `_IO_file_doallocate`); with it the run is clean. Building with `-DJSON_DISABLE_UNLOCKED_FILE_IO=1` is clean as well.
- All seven parse fuzzers (JSON, CBOR, MessagePack, UBJSON, BJData, BON8, BSON) run clean under MSan on a few small inputs.
- `unit-file_input` and `unit-deserialization` pass.

### Breaking changes

No breaking changes. Only MemorySanitizer builds change, and only in how a `FILE*` is read (`std::fgetc` instead of `getc_unlocked`): results are identical, and the public API is unchanged. The `_dufio` ABI tag still follows `JSON_DISABLE_UNLOCKED_FILE_IO` only. That does no harm, because MSan objects cannot be linked with non-MSan objects anyway.
