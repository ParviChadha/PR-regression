# Pull request #5837: Move elements when converting rvalue containers to JSON

## Description
`json j = std::move(container)` now moves the elements instead of copying them. Previously the only generic `to_json` overloads took `const CompatibleArrayType&` / `const CompatibleObjectType&`, so every string in a `std::vector<std::string>` was copied.

## Change
- New `to_json(j, C&&)` overloads for array-like and object-like containers, which build the array/object via `std::make_move_iterator` (`external_constructor::construct_moving`).
- Constrained to non-lvalue, non-const types with the same compatibility traits as the `const&` overloads. Excluded: `array_t`/`object_t` (have their own rvalue overloads), `std::vector<bool>`, `std::filesystem::path` and `std::u8string` (dedicated overloads), range views, enum-keyed maps.
- `std::valarray`: its existing overload only moves a `const` object and still copies. It is untouched and still copies (a valarray rvalue goes through that overload, not the new one).
- Map keys are `const` and still copied. `std::map::extract` (C++17) to move keys too was not pursued.

## Measurements
`std::vector<std::string>` (100k × 40 chars): 4.7 → 2.3 ms; `std::map<std::string,std::string>`: −18 %; `vector<int>`, nested vectors, `vector<json>`: unchanged.

## Public API
No breaking changes to the API: it is additive (no signature removed or changed), and the new overloads are only selected for rvalue containers. Two **behaviour** changes for code converting rvalue containers:
1. **Moved-from source:** after `json j = std::move(v);` the elements of `v` are in a valid but unspecified state (previously untouched). Lvalues and `const` rvalues are still copied and unchanged.
2. **Exception guarantee:** the JSON value is still unchanged on failure, but if an exception is thrown mid-conversion (e.g. allocation failure), the source may be partially moved-from, so the strong guarantee no longer holds for the source of an rvalue conversion.

Both are documented in `basic_json.md` (constructor 3 and its exception-safety section) and in the release notes page.

## Tests
New `unit-to_json-rvalue.cpp` (move-tracking element type; lvalue/const rvalue copy and are untouched; deque, list, forward_list, array, set, vector<bool>, valarray, maps, `path`/`u8string`, a user type with its own `to_json(json&, T&&)`). Verified with clang in C++11/17/20; full unit suite builds and passes at C++17, and the affected suites (udt, udt_macro, constructor1/2, regression1/2, alt-string, conversions1/2, ordered_*, …) at C++11 and C++20. A first prototype regressed `std::filesystem::path` and `std::u8string` (caught by unit-conversions2); fixed here.

## Discussion before merge
- nlohmann: Decision on the two behaviour changes: **accepted as documented** (the moved-from source and the strong exception guarantee that no longer covers the source of an rvalue conversion).

- **Moved-from source:** the new overloads are only selected for non-const rvalues. That is either a temporary, which nobody can observe afterwards, or an explicit `std::move(v)`, which already means the caller is done with `v`.
- **Consistent with the existing overloads:** rvalue `string_t`, `binary_t`, `array_t` and `object_t` have long had moving `to_json` overloads, so `json j = std::move(str)` already empties `str`. Copying a `std::vector<std::string>` while moving a `std::string` was the inconsistent part.
- **Exception guarantee:** this cannot be kept cheaply.
