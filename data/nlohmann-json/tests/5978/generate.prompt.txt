# Pull request #5978: accept() checks strings without copying them

## Description
`json::accept()` parses with `json_sax_acceptor`, which ignores string values and object keys. The lexer still copied every string token into its token buffer. On twitter.json that copy was 18 % of the instructions of `json::accept()` (x86, GCC 16, callgrind).

## Change

- The lexer flag that `accept()` sets is renamed from `discard_number_values` to `discard_values`, because it now covers strings too.
- With the flag set, `scan()` calls a second instantiation of `scan_string()` (tag dispatch on `std::integral_constant<bool, Keep>`). It runs the same checks with the same error messages but never writes to the token buffer. The checks cover escapes, surrogates, UTF-8 and control characters.
- `scan()` picks the instantiation once per string. A run-time check inside the string loop made number-heavy files up to 3 % slower on Apple M1.
- New test in `unit-class_parser.cpp`: `accept()` must agree with `parse(..., allow_exceptions=false)` on 127,800 cases. Each case is an escape, a surrogate, broken UTF-8 or a control character, placed at every position from 0 to 70 in five document shapes. The test covers all comment/trailing-comma options and string, stream and `std::list` iterator input. The test fails on a deliberately broken lexer.

## Performance

`json::accept()` over 19 files. Each number is time after / before: the median of per-pair ratios from one binary that alternates both versions, geometric mean over several code layouts.

Environment:
- x86: Haswell VPS, `-O3 -march=haswell`.
- Mac: Apple clang 21.

On Apple M1 the change cuts instructions by 18–20 % on string-heavy files, but time drops much less: the core hides most of the copy. tree-pretty is the only file that is slower anywhere, by 0.6–0.9 % on M1. Without loop alignment, twitter and tree-pretty measured up to 1.4 % slower on M1, which turned out to be loop placement.

## Testing

- A differential fuzz compared old and new `accept()` over all option combinations, with and without `JSON_DIAGNOSTICS`, on about 19 M inputs: no mismatches. Deliberately broken variants were caught.
- Full ctest with ASan and UBSan: 184/184 passed.
- GCC 16 and Clang 22 with the CI warning flags, C++11 and C++20: no diagnostics.

## Breaking API changes

None. The renamed flag is a parameter of `detail::lexer`/`detail::parser` and of `basic_json::parser()`, which is private outside the tests. `accept()` returns the same results as before.
