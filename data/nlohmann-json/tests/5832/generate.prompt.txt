# Pull request #5832: Fix quadratic parent updates for ordered_json with JSON_DIAGNOSTICS

## Description
With `JSON_DIAGNOSTICS=1`, `set_parent()` called the full `set_parents()` for `ordered_json` on every call: `push_back`/`emplace_back`, `at()`, and `operator[]`/`at()` on existing keys. Building an `ordered_json` array was therefore quadratic.

## Changes
- `at()` and array append set only the one child's `m_parent`.
- Object `operator[]`/`push_back`/`emplace` record the container capacity before the insert and call `set_parents()` only if it changed. Arrays and objects share one `container_capacity()` and one `set_parent_after_insert()` helper (arrays report their `capacity()`; for objects, only the node-based standard containers (`std::map`, `std::multimap`, `std::unordered_map`, `std::unordered_multimap`) report 0 = never moves, only `nlohmann::ordered_map` reports its `capacity()`, and any other object type reports unknown = always re-parent).
- `update()` (all overloads, incl. `merge_objects` and the iterative variant) now assigns through `operator[]` instead of calling `set_parent()` per key; `merge_patch()` already goes through `operator[]`, so it benefits too. `erase` keeps its `set_parents_after_object_erase()` (O(n) for `ordered_map` anyway).
- Remove the redundant `set_parents()` in the copy constructor (`copy_level`/`copy_iteratively` already re-parent each level). The move constructor keeps its `set_parents()` (required).
- New tests: parent-pointer invariant checker (`json` and `ordered_json`) across parse, copy, move, copy-assign, swap, push_back/emplace_back/emplace/operator[] growth and `at()`; `update()` (both overloads, `merge_objects`) and `merge_patch()` on `json`/`ordered_json` checking parents and diagnostic paths. No timing test (would be flaky).

## Numbers (ordered_json, nested-array push_back, -O2, diagnostics on)
| n | before | after |
|---|---|---|
| 25k | 101 ms | ~8 ms |
| 50k | 412 ms | ~5 ms |
| 100k | 1635 ms | ~11 ms |
| 200k | 6482 ms | 27 ms |

`ordered_json::update()` with 20k new keys: 372 → 295 ms (no diagnostics: 259 ms), i.e. the diagnostics overhead is gone; the rest is `ordered_map`'s inherent linear key lookup (100k keys: 14.0 → 10.0 s).

`at(i)` x10000: 31.7 → 0.017 ms. Parse unchanged; copies −5–8 % with diagnostics.

## Breaking changes
None. No public API change; behaviour without `JSON_DIAGNOSTICS` is unchanged.

Tested with `-DJSON_DIAGNOSTICS=1`: unit-diagnostics, unit-ordered_json, unit-element_access1/2, unit-modifiers. `make amalgamate` run.
