# Pull request #6119: Report a missing 0xFF after a final BON8 string also without strict

## Description
Fixes #6110.

## Problem

A BON8 string ends at the first byte that cannot continue it. When a string ends a value and is not terminated by 0xFF, that byte belongs to whatever follows the value. The reader has already taken it from the input and keeps it in its push-back buffer. With `strict = true` the end-of-input check reports it. With `strict = false` the buffer was discarded, so the next read from the same stream started behind it, and a following value lost its first byte or bytes without an error:

| input (two values in one `std::istringstream`) | first `from_bon8(s, false)` | second `from_bon8(s, false)` |
|---|---|---|
| `61 90` | `"a"` | the `0` is gone |
| `61 C2 41 90` | `"a"` | `0` instead of the integer `C2 41` |

[`bon8.md`](https://json.nlohmann.me/features/binary_formats/bon8/) already says that "a string at the very end of a message must be terminated by 0xFF". This applied only with `strict = true`.

## Change

`binary_reader::sax_parse` now reports `parse_error.110` ("string at the end of the value is not terminated by 0xFF") when a BON8 value is complete, `strict` is false and the push-back buffer is not empty. The position and "last byte" are the first byte that does not belong to the value, as in the strict message for the same input. With `strict = true` nothing changes.

Giving the bytes back to the input instead was considered and rejected: `sputbackc`/`ungetc` guarantee only one byte (the `C2 41` case needs two), and the bulk windows of the stream and `FILE*` adapters would have to rewind too. That is a lot of code for input the format calls invalid.

Docs: `from_bon8.md` (exceptions) and `bon8.md` (non-canonical input) describe the new case.

## Tests

- `unit-bon8.cpp`: the two assertions that pinned the old behaviour (`{0x81, 'a', 0x90}` and `{0x81, 'a', 0xC2, 0x00}` accepted with `strict = false`) now expect the exception. New stream cases: a terminated string leaves the next value in the stream (`tellg() == 2`, the next read gives `0`), and an unterminated one throws. Passes in C++11 and C++17, with `JSON_DIAGNOSTICS=0` and `=1`, under ASan and UBSan (908,428 / 908,431 assertions).
- The 14 other test files that read BON8 pass unchanged (class_parser, class_lexer, binary_formats, guard-page, recursion_depth_limit, the custom-type tests, ...). The BON8 fuzzer uses `strict = true` and is not affected.
- Round trip: 50,269 random values written with `to_bon8`, concatenated in groups of 1 to 5 into one stream, and read back one by one with `strict = false`: all equal. `to_bon8` always writes the final 0xFF, so canonical input is not affected.
- clang-tidy (CI configuration) is clean.

## Breaking changes

None against a release: BON8 is new in 3.13.0. Compared with develop, non-canonical input (a final string without 0xFF followed by more bytes) read with `strict = false` now throws `parse_error.110` (or returns a discarded value with `allow_exceptions = false`) instead of returning the value and dropping the following bytes. This applies to pointer, iterator and container input as well, where the dropped bytes could not be observed. Fixing it now keeps that behaviour from being part of the first release.

## Linked issue #6110: from_bon8 with strict = false drops the bytes after a final string that has no 0xFF terminator
### Description
A BON8 string has no length and ends at the first byte that cannot continue it. When a string is the last thing in a value and is not terminated by `0xFF`, that ending byte (or two bytes, for an integer such as `C2 41`) belongs to whatever follows the value. The reader takes it from the input, keeps it in its private push-back buffer, and finishes the value. With `strict = true` the end-of-input check reads the buffer and reports trailing data. With `strict = false` the buffer is simply discarded, so the next read from the same stream starts behind the lost bytes, without any error.

The documentation promises two things that this contradicts:

- [BON8](https://json.nlohmann.me/features/binary_formats/bon8/): "Input that ends prematurely, trailing data after the value, and a missing final 0xFF after a string at the end of the message are reported as parse_error.110." and "a string at the very end of a message must be terminated by 0xFF."
- [Parsing large and partial input](https://json.nlohmann.me/features/parsing/large_and_partial_input/): "`from_cbor` and its relatives accept `strict = false` to stop after the first value and leave the rest of the stream untouched".

With `strict = false`, the input `61 90` (the string `"a"` directly followed by the integer `0`) is accepted as `"a"`, and the following `from_bon8` call on the same stream finds nothing. With `61 C2 41 90`, the two-byte integer `C2 41` is lost and the next call silently returns `0`, a wrong value rather than an error.
