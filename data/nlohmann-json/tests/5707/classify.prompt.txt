# Pull request #5707: Round-trip BJData ND-array annotations exactly (single precision, key order)

## Description
## Summary

`to_bjdata()` encodes a JData-annotated object (`_ArrayType_`, `_ArraySize_`, `_ArrayData_`) as a compact BJData
ND-array in two cases where `from_bjdata()` then returned a different value, breaking the documented guarantee
that "an object is only converted if the annotation describes a packed array that is parsed back into the same
annotated object." (1) A `"single"` element that is finite and in range but not exactly representable as `float`
(e.g. `0.1`) or that underflows to `0` (e.g. `1e-300`) was silently narrowed instead of falling back to a plain
object, unlike out-of-range integer elements. (2) `from_bjdata()` returned the annotation keys in the order
`_ArraySize_`, `_ArrayType_`, `_ArrayData_` instead of the documented `_ArrayType_`, `_ArraySize_`, `_ArrayData_`,
which made a round trip of an `ordered_json` compare unequal even though the values themselves were preserved.

## Changes

- `write_bjdata_ndarray()` (`binary_writer.hpp`): a `"single"` `_ArrayData_` element is now only treated as
  in-range if `static_cast<float>` and back reproduces the original `double`, the same criterion
  `write_compact_float()` already uses for CBOR/MessagePack (with the same `-Wfloat-equal` suppression). Otherwise
  the object falls back to a plain object encoding, as out-of-range integer elements already do.
- `get_ubjson_size_value()` / `get_ubjson_size_type()` / `get_ubjson_array()` (`binary_reader.hpp`): the ND-array's
  element type marker precedes the dimension vector on the wire, so it is now passed down to where the annotation
  object is opened and the `"_ArrayType_"` key is emitted there, before `"_ArraySize_"`, matching the order used
  throughout the documentation. `get_ubjson_array()` no longer re-does the type-name lookup and emission.
- `docs/mkdocs/docs/features/binary_formats/bjdata.md`: clarified the round-trip requirement for `"single"`
  elements and documented the fixed `_ArrayType_`, `_ArraySize_`, `_ArrayData_` key order.

## Tests

Added to `tests/src/unit-bjdata.cpp`:
- Two cases in "ndarray with out-of-range `_ArrayData_` elements stays as object": a `"single"` element that is
  not exactly representable as `float` (`0.1`), and one that underflows to `0` (`1e-300`); both must fall back to
  a plain object and round-trip exactly.
- A new section, "ndarray annotation keys are read back in the documented order": an `ordered_json` round trip of
  the documented example must compare equal (and dump identically).

Verified all six new assertions fail against develop's headers (`633de8e44`) and pass with the fix. Built and ran
`tests/src/unit-bjdata.cpp` with `-Wall -Wextra -Werror -fsanitize=address,undefined` (and `-Wfloat-equal`) for
`-std=c++11`, `-std=c++17`, and `-std=c++20`; all 32 test cases (667300 assertions) pass in every configuration.
The existing "SAX aborts" ndarray sub-tests were re-derived for the new key emission order (four countdown values
changed; the total event count and everything from `_ArrayData_` onward is unchanged) and pass.

## Public API

No breaking changes. `get_ubjson_size_value()` gained a defaulted `ndarray_dtype` parameter, which is
private/internal (`binary_reader` is a detail class); `from_bjdata()`'s return value for the two fixed cases
changes to match the documented behavior, which is a bug fix, not an API change. `ordered_json::from_bjdata()`
now returns annotation keys in a fixed order instead of an order that depended on the input; this was never
documented as unspecified.

### Description

`to_bjdata()` encodes a JData-annotated object (`_ArrayType_`, `_ArraySize_`, `_ArrayData_`) as a BJData ND-array in two cases where `from_bjdata()` then returns a different value.
