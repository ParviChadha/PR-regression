# Pull request #6075: Read a std::u8string from a JSON string and store it as one in every configuration

## Description
In C++20, `json(std::u8string)` was stored as a JSON string only when `std::filesystem::path` support was available (the `to_json` overload sat inside the `JSON_HAS_FILESYSTEM` guard), and there was no matching `from_json`, so `get<std::u8string>()` threw `type_error.302` ("type must be array, but is string"). Without `std::filesystem` the same expression still produced an array of code units, the 3.12.0 behaviour. So the same source gave different JSON types depending on the configuration, and the stored value could not be read back.

## Change

- Move the `to_json` overload out of the filesystem guard, so that a `std::u8string` is a JSON string in every configuration. The value is built directly from the code units, which also works for a custom `string_t` such as the tests' `alt_string`.
- Add a `from_json` overload for `std::basic_string<char8_t>` that reads a JSON string. The array of numbers written by 3.12.0 is still accepted; other types throw `type_error.302` ("type must be string or array").
- `std::u8string_view`, `char8_t` arrays and `const char8_t*` are unchanged (they still produce arrays of code units, as in 3.12.0). `std::filesystem::path` still round-trips.
- Documented in `home/releases/unreleased.md`, `basic_json.md`, `get.md` and `template_parameters.md`.

## Tests

- `unit-conversions2.cpp`: the `std::u8string` case now covers ASCII and UTF-8 content, round trips (`get`, `get_to`, embedded NUL, `vector`, `map`), the old array form, wrong types, `ordered_json`, and the unchanged `u8string_view` and `char8_t` arrays. The file now also mentions `JSON_HAS_CPP_20`/`_23`, so it is built as `_cpp20` and `_cpp23` as well (the test previously never ran in C++20 under CMake).
- A new target `test-conversions2_no_filesystem` runs it with `JSON_HAS_FILESYSTEM=0` and `JSON_HAS_EXPERIMENTAL_FILESYSTEM=0`.
- `unit-alt-string.cpp` gets a test with a custom string type.
- The new tests fail on `develop` (`get<std::u8string>` throws; without `std::filesystem` the value is an array) and pass with the change. Passes with clang 21 and g++ 16 in C++11/17/20/23, and with `JSON_DIAGNOSTICS=1`. The full unit suite passes under ASan and UBSan. Compile time and conversion benchmarks (`std::string`, `std::vector<int>`, `std::filesystem::path` to JSON) show no regression; the path conversion retires about 3 % fewer instructions.

## Breaking changes

This is a behaviour change relative to 3.12.0 for C++20 code with `__cpp_lib_char8_t`, although it is not a source break and no signature was removed.

- **Who is affected:** code that converts a `std::u8string` to JSON and then looks at the JSON form: `is_array()` checks, reading it as `std::vector<char8_t>` or `std::vector<std::uint8_t>`, or comparing the serialised output with `[...]`. Such a value now serialises as a string. The change is transitive: a `std::u8string` inside a `std::vector`, `std::pair`, `std::tuple`, `std::optional` or as a `std::map` key also becomes a string.
- **Not affected:** reading old data (`get<std::u8string>()` still accepts the 3.12.0 array), code that only round-trips a `std::u8string`, and anyone already on current `develop` with `std::filesystem` available, where it was already a string.
- **Mitigation:** build the array form explicitly, e.g. `json(std::vector<char8_t>(s.begin(), s.end()))`.
