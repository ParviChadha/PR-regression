# Pull request #6030: Scan the buffer of a FILE in bulk with glibc and the Apple C library

## Description
## Summary

Parsing from a `FILE*` still read one character at a time through `getc_unlocked()`, while a `std::istream` has its get area scanned in bulk. `file_input_adapter` now offers the lexer the same kind of window into the buffer of the `FILE`.

It reads the fields that the C library's own `getc_unlocked()` macro reads:

- glibc: `_IO_read_ptr` and `_IO_read_end`,
- Apple: `_p` and `_r`.

It consumes exactly the characters `getc_unlocked()` would return, so the file is left where it was left before. When the buffer is about to be refilled, the part of the current token in it is kept for error messages, as for streams.

The window needs the file locked for the whole parse, so `JSON_DISABLE_UNLOCKED_FILE_IO` and MemorySanitizer builds turn it off, and the docs of that macro say so. uClibc defines `__GLIBC__` but has other fields, so it does not get the window. Other C libraries keep `getc_unlocked()` / `_fgetc_nolock()` / `std::fgetc` as before. The idea is gnulib's `freadptr()` / `freadseek()`.

## Measurements

| | Apple M1 Max | x86-64 (glibc, GCC 15 / Clang 21) |
|---|---|---|
| `parse(FILE*)` | 2.0–2.6× | 1.7–2.2× |
| `accept(FILE*)` | 3.0–4.1× | 2.9–4.4× |

The rows are for `twitter.json`, `citm_catalog.json` and `canada.json`. Parsing from a `FILE*` is now about as fast as from a `std::ifstream`. In the Google Benchmark suite, `ParseFILE/*` is 2.3–3.1× as fast, and the binary readers from a `FILE*` (`FromMsgpack/*`, `FromBinaryFile/*`) 1.3–1.8×.

## Tests

New sections of `unit-file_input.cpp`, on macOS and on glibc (Docker, GCC, ASan):

- FILE buffers of 1 to 70 bytes and unbuffered files, against parsing from a string: values, exception messages and `accept()`,
- characters pushed back with `ungetc()` before parsing,
- SAX events at the same file positions with small buffers,
- CBOR strings across the edges of the buffer.

They also pass with `JSON_DISABLE_UNLOCKED_FILE_IO=1`. `fuzzer-parse_json` compares `FILE*` with pointer input and ran 4.4 M executions with this change without a finding.

## Notes for review

- `JSON_FILE_WINDOW` is set next to `JSON_UNLOCKED_FILE_IO` and undefined at the end of the header.
- This PR and #6031 both change one paragraph of `docs/mkdocs/docs/features/performance.md`. Whichever is merged second needs a small conflict resolution there.

## Breaking changes

No breaking changes. The public API is unchanged, and the file is left in the same state after parsing. As before, the file is locked for the whole parse.
