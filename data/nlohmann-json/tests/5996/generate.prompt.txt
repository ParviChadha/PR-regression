# Pull request #5996: insert(): strong guarantee for single elements, basic guarantee for the rest

## Description
Fixes #5986.

The docs for `insert()` promised the strong exception guarantee for every overload, but a failed copy of a new element could leave the value changed. With `JSON_DIAGNOSTICS`, the value was even left invalid: stale parent pointers made the next `assert_invariant()` abort. After the [discussion](https://github.com/nlohmann/json/pull/5996#issuecomment-6571792055) of what the standard containers guarantee, this PR no longer builds a rollback on top of `array_t`/`object_t`. Instead it documents the guarantees that `insert()` actually gives, and fixes the two places where it fell short of them.

### Changes (`basic_json::insert`)

- **`insert(pos, const basic_json&)`:** at `end()`, forwards as before (`std::vector` has no effects there). Anywhere else, copies the value first and inserts it by move, as libstdc++ does internally. libc++ shifts the tail before copying, so a failed copy left an extra `null` behind.
- **Parents:** `insert_iterator()` and the object `insert(first, last)` set the parents in a scope guard, which also runs when an exception is thrown. A failed insertion now leaves a valid value with `JSON_DIAGNOSTICS` as well. Without `JSON_DIAGNOSTICS` the guard does nothing.
- **Docs (`insert.md`):** strong guarantee for (1); basic guarantee for (2)–(5): if copying the new elements throws, the value may be partially modified but stays a valid array or object. The argument checks throw before anything changes. This matches what `std::vector::insert` ([vector.modifiers]) and `std::map::insert` ([associative.reqmts.except]) promise when copying `T` allocates, and what `update()` already documents.

### Tests

`unit-allocator.cpp`, "insert() provides its documented exception guarantees (#5986)": fails every allocation in turn for all overloads, with `json` and `ordered_json`, with and without spare capacity, inserting in the middle and at the end. For (1) it checks that `dump()` is unchanged. For (2)–(5) it checks that the value keeps its type, that every child names its parent, and that a copy succeeds.

Mutation checks: dropping the copy-first step fails the strong check on libc++, and dropping the guard aborts in `assert_invariant()` with `JSON_DIAGNOSTICS`. With the fix, the test passes on Apple clang (ASan+UBSan) and on GCC 16 (libstdc++, `-Wall -Wextra`, no warnings), with and without `JSON_DIAGNOSTICS`. The full `ctest` with ASan+UBSan passes 182/182. A program that calls every overload compiles and runs with `-fno-exceptions -DJSON_NOEXCEPTION`.

### Performance

Mac instruction counts from the A/B harness, develop → this PR. Each repetition copies a 100-element array or a 16-member object, then makes one insert (8-element sources):

| row | json | ordered_json |
|---|---|---|
| single int, middle / end | 1.007 / 1.005 | 1.007 / 1.006 |
| single string, middle / end | 1.008 / 1.005 | 1.006 / 1.005 |
| single array, middle | 0.998 | 1.006 |
| count int, middle / end | 1.000 / 0.991 | 1.000 / 1.000 |
| count string, middle | 1.000 | 0.995 |
| range int, middle / end | 1.000 / 1.000 | 1.000 / 1.000 |

Every row is within 1 %. The single-element inserts pay about 40–60 instructions for the end check and the extra move. On the same workload, the previous version of this PR (rotate and rollback) cost +6–12 % on count and range inserts in the middle, and +2–5 % on object inserts into non-empty objects.

### Public API

No source or ABI changes. The documented exception guarantee of `insert()` overloads (2)–(5) is now basic instead of strong. This only documents what every 3.x release has done: the strong wording for these overloads arrived with the API docs in 3.10.0 and the code never provided it. Overload (1) now actually provides its strong guarantee.

## Linked issue #5986: insert() does not provide its documented strong exception guarantee; a failed insert leaves stale parent pointers with JSON_DIAGNOSTICS
### Description

[`insert()`](https://json.nlohmann.me/api/basic_json/insert/#exception-safety) documents for all five overloads: *"Strong exception safety: if an exception occurs, the original value stays intact."* That does not hold when an allocation fails while the elements are copied: the value is modified, and with `JSON_DIAGNOSTICS` the parent pointers of the surviving elements are left stale, so the next operation that checks the invariant aborts. Three related symptoms:

**(1) Object range insert keeps the members inserted before the throw.** `insert(first, last)` for objects calls `m_data.m_value.object->insert(first, last)` directly ([json.hpp#L5087](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/json.hpp#L5087)); `std::map::insert(first, last)` and `ordered_map::insert` only give the basic guarantee. With `{"a":1}` and a three-member source, a `bad_alloc` on the 4th allocation leaves `{"a":1,"m":"xxx…"}` (libc++ and libstdc++; `ordered_json` at k = 8).

**(2) Array inserts with a throwing element copy modify the array.** `insert(pos, const basic_json&)`, `insert(pos, cnt, val)` and `insert(pos, first, last)` forward to `std::vector::insert` in `insert_iterator()` ([json.hpp#L4921-L4927](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/json.hpp#L4921-L4927)). The standard gives `vector::insert` the "no effects" guarantee only for a single element at the end when the element's copy constructor throws, and `basic_json`'s copy constructor allocates for strings and containers. Observed:

| overload | capacity | libc++ (Apple clang 21) | libstdc++ (GCC 16) |
|---|---|---|---|
| `insert(pos, val)` in the middle | spare (as after any `erase()`) | `[1,2,3]` → `[1,null,2,3]` | intact |
| `insert(pos, 3, val)` in the middle | spare | three `null`s inserted | three `null`s inserted |
| `insert(pos, first, last)` in the middle | spare | `null`s inserted | `null`s inserted

### What the standard promises

**`std::vector::insert`**, [[vector.modifiers]](https://eel.is/c++draft/vector.modifiers) (C++11: [23.3.6.5/1](https://timsong-cpp.github.io/cppwp/n3337/vector.modifiers#1)):

> If an exception is thrown other than by the copy constructor, move constructor, assignment operator, or move assignment operator of `T` or by any `InputIterator` operation, there are no effects. If an exception is thrown while inserting a single element at the end and `T` is *Cpp17CopyInsertable* or `is_nothrow_move_constructible_v<T>` is `true`, there are no effects.
