# Pull request #5929: Validate the UBJSON/BJData container type marker for count 0; fix UBJSON docs

## Description
## Summary
- The `$` type marker of an optimized container was only checked when an element was read, so `[$x#i0`, `{$x#i0` and `[$E#i0` parsed as empty containers although `[$x#i1 …` is rejected and the specification requires a legal marker after `$` (py-ubjson rejects it too). `get_ubjson_size_type` now validates the marker right after `$`: UBJSON allows `Z N T F i U I l L d D H C S [ {`; BJData `B U i u I m l M L h d D C` (existing exclusions unchanged). The function is shared, so BJData is fixed too.
- UBJSON docs corrected and completed: `N` vs `Z`, `$` requires `#`, NaN/Infinity, the `H` row, `use_type` semantics, long `Z/T/F` arrays, exception lists, duplicate keys.

## Breaking changes
No API or ABI change. Input that was accepted is now rejected with `parse_error.112`: an optimized `[` or `{` container with a `$` marker that is not legal for the format and count 0 (`5B 24 78 23 69 00`, `7B 24 78 23 69 00`, `[$E#i0`; in UBJSON also the BJData-only markers `B u m M h`). They used to return `[]`/`{}`. Valid input is unaffected (differential fuzz of ~2M inputs against the previous code: no valid input changed). `[$#` now reports 112 instead of 110.

## Stack
This PR is part of a stack of six PRs from a review of the binary formats against their specifications and other implementations (CBOR → MessagePack → UBJSON → BSON → BJData → BON8). Please merge in that order.

## Commit message
* Validate the optimized-container type marker for count 0 in UBJSON and BJData

The '$' type marker of an optimized container was only checked when an
element was read, so containers with count 0 accepted any marker:
`[$x#i0`, `{$x#i0` and `[$E#i0` parsed as empty containers although a
non-empty container with the same marker is rejected and the UBJSON
specification requires a legal marker after '$'.

get_ubjson_size_type() now checks the marker right after '$' against the
allowed set (UBJSON: Z N T F i U I l L d D H C S [ {; BJData: B U i u I m
l M L h d D C, with the existing exclusion of T F Z N S H [ {) and reports
parse_error.112 "marker ... is not a permitted optimized array type".

Input that was accepted and is now rejected: an optimized container with
count 0 and an invalid '$' type marker. Valid input is unaffected. Two
existing tests that used an invalid marker incidentally ("[$#" and a
negative-count case) were adapted.

Signed-off-by: Niels Lohmann <mail@nlohmann.me>

* Correct and complete the UBJSON documentation

Fix statements that disagree with the behavior (checked with probes):
- `Z` is null; the unused marker is `N`.
- `$` requires `#`; use_type with use_size=false throws other_error.502 only
  for non-empty arrays, objects and binary values.
- NaN and infinity are written as IEEE 754 float64 and read back unchanged;
  the UBJSON specification encodes infinity as null.
- `H` is documented (semantics, parse_error.115, out_of_range.406); the
  "complete mapping" claim is qualified.
- use_type "same type" means same marker.
- Long Z/T/F arrays lose only the `$` annotation; the `#` count and the
  element markers are kept.
- from_ubjson lists the 112, 113, 115, 406 and 408 causes that occur for
  UBJSON, without the BJData-only ND-array wording.
- Duplicate object keys keep the last value; the `$` type marker is
  validated even for count 0.
- Smaller fixes: float32 row, "map" -> "object", https link, exception 110
