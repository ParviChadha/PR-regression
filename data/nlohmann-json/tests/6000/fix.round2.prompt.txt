# Pull request #6000: Do not construct the base class when destroying a container

## Description
Fixes #5995.

## What

`json_value::destroy_container()` and `destroy_walk()` (both `noexcept`, reached from `data::~data()`) held the containers they tear down in default-constructed `basic_json` stand-ins. Each one constructs a `CustomBaseClass` that belongs to no value: one per destroyed container, four per level in `destroy_walk()`. A base class whose default constructor allocates (a long `std::string` member, say) made destruction allocate again, and terminate when that allocation failed, which is what #5762 set out to prevent (#5135).

The stand-ins now are `data` (`m_type` and `m_value`, no base class). `struct data` is forward-declared before `union json_value`, and `take`, `has_no_children`, `all_children_leaves`, `walk_child`, `pop_walk_child`, `free_container`, `destroy_bounded` and `destroy_walk` take `data&`; real children are passed as `child.m_data` / `child.second.m_data`. The algorithm itself is unchanged. `take()` already moved only `m_data`, so `m_parent` under `JSON_DIAGNOSTICS` is handled as before.

## Tests

`unit-custom-base-class.cpp`, "destroying a value does not construct the custom base class": a counting base class checks that destroying a scalar, a small array/object document and a value nested 1000 levels deep (alternating arrays and objects, so `destroy_walk()` walks both) constructs no base object and destroys exactly one per value. Without the fix: 1 construction and one extra destruction per case.

The reproducer from the issue (allocating base class under a fail-at-k `operator new`) now ends with `no throw at k=12: done`, with and without `JSON_DIAGNOSTICS=1`; before, it terminated.

Not addressed here (mentioned in the issue as related): the unconditional `noexcept` on `basic_json(basic_json&&)` with a base class whose move constructor can throw.

## Public API

No breaking changes. Only private members of `json_value` change their parameter types.

## Linked issue #5995: ~basic_json() default-constructs the CustomBaseClass for every destroyed container; an allocating base class can still terminate on std::bad_alloc (#5762 incomplete)
### Description

#5762 made destruction allocation-free so that "destroying a value never allocates and never calls `std::terminate` because an allocation failed" (#5135). That holds for the default base class, but not for a `CustomBaseClass`: `json_value::destroy_container()` and `destroy_walk()` tear a container down through a stand-in declared as a full `basic_json` (`basic_json cur;`), and a default-constructed `basic_json` default-constructs the base class. So

1. every destroyed array or object default-constructs and destroys one base object that belongs to no value (four per level in `destroy_walk()`, i.e. for values deeper than the recursion limit), and
2. a base class whose default constructor allocates (a `std::string`, `std::vector` or `shared_ptr` member with a non-empty default) makes destruction allocate again inside the `noexcept` destructor; if that allocation fails, the process terminates, exactly what #5762 set out to prevent.

The documented requirement for `CustomBaseClass` is only "default-constructible, non-`final`" (`json_base_class_t.md`), so such a base is within contract. 3.12.0 terminated in the same situation for every base class (that was #5135); develop is better for non-allocating bases and unchanged for allocating ones.
