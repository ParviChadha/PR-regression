# Pull request #5824: Speed up writing CBOR and MessagePack, above all integer arrays

## Description
Writing CBOR or MessagePack from integer-only arrays was no faster on `develop` than in 3.12.0, and with GCC it was slower (ToCbor/*_ints at 0.84–0.93×), although #5286 had made binary writing non-virtual. This PR makes `to_cbor()` and `to_msgpack()` faster than both 3.12.0 and `develop` on every benchmark below, with byte-identical output.

## Cause

- **No single commit.** On clang the difference was noise (±3%, no step anywhere between 3.12.0 and `develop`). On GCC 13 it accumulated gradually, in steps smaller than the noise.
- **The append.** Each number's 1–8 payload bytes were appended with `vector::insert()`, which libc++ and libstdc++ both implement as an out-of-line insert-anywhere routine. In a profile this was 30% of the time, more than encoding the number, so removing the virtual call in #5286 didn't help. GCC also kept the small sink functions out of line.
- **Branch mispredictions.** The type switch (positive integers are `number_unsigned`, negative ones `number_integer`), the sign test and the 1/2/4/8-byte length ladder mispredict on mixed data. They accounted for about 40% of what remained.

## Changes

**1. Append to the output vector through a position-tracking sink**
- `output_vector_sink` keeps its own write position. It grows the vector geometrically ahead of that position with `resize()`, reusing any capacity the vector already has, and copies each write there.
- Its destructor shrinks the vector to the written length, also when a write throws. That makes the sink move-only.
- Writes of 256 bytes or more that don't fit are appended with `insert()` plus geometric headroom, so a large string or binary value is copied once instead of being zero-filled and then copied.
- `output_vector_adapter` (the `to_*(j, vector)` overloads) appends with `push_back()`/`insert()` again, so a caller holding the adapter never sees the space kept ahead.

**2. Write CBOR integers without branching on their sign or size**
- `number_integer` and `number_unsigned` share one case; the sign is applied with a mask.
- An integer's head is built without branches: the size class comes from a table indexed by `count_leading_zeros()`, and the head is stored as one byte plus one 8-byte word, of which only the needed bytes are kept. Heads of strings and containers keep the branching `write_cbor_head()`, since their lengths are mostly predictable.
- Arrays are written by an out-of-line `write_cbor_array()`. Inlined into `write_cbor`, its loop made every call of `write_cbor` save more registers, which cost citm_catalog 13%.
- Runs of integers are encoded straight into space reserved from the sink with the new `reserve()`/`commit()`, so the write pointer stays in a register.

**3. Write MessagePack integers without branching on their sign or size**
- MessagePack takes the same approach, with the integer code factored into helpers both formats share: `integer_bits()` (the 64 bits and the sign mask), `integer_size_class()` (the table lookup), `encode_first_byte_and_tail()` (the one-byte plus 8-byte-word store) and `write_array_elements()` (the run loop).
- Only the first byte is format-specific. For a negative `n`, the size class comes from `2 * (-1 - n) + 1`: `n` fits int 8/16/32 exactly when that value fits uint 8/16/32, so one table lookup serves both signs. The fixint limit (127, or −32) is selected through a mask, and the marker is `0xCB + class` (uint) or `0xCF + class` (int).
- The new path picks the format from the low 64 bits, so number types wider than that keep the previous range checks.
