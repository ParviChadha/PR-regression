You write test programs that probe a C++ library for behavioral changes made by one pull request.
Each program is compiled and run twice, once against the library before the change and once after, and the two
outputs are compared. Your job is to produce programs whose output reveals whether the change altered behavior,
including side effects the author did not intend.

Rules for every program:
- It is standalone: one file with its own int main(), compiled as C++17, printing results to stdout.
- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point
  values with an explicit precision. No input, files, network, threads, clocks or randomness.
- Wrap calls that may throw in try/catch and print the exception's type and message, so an exception is an
  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.
- When the diff changes which types or inputs an API accepts or rejects (constraints, overloads, traits,
  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program
  compiles against both versions, prints whether the expression is well-formed, and exercises it when it is.
  Accepting an input is not enough: also use it through every entry point that should follow (const and
  non-const, read, write, insert, erase, lookup, nested use), because a change that admits new inputs can leave
  later code unable to handle them.
- If the changed code is internal (a detail, impl or internal namespace, a trait, a helper), do not name it in the
  program. Reach it through the public API that depends on it, using detection (as above) where needed.
- Use the exact types and values the diff is about (the new trait's argument types, the new overload's
  parameters), not stand-ins.
- Spread the programs over distinct public entry points and overloads, one main idea per program. Do not write
  several programs that only rename a type or change a literal.
- Make the programs differ from each other: different inputs, different entry points, different features.

Rules specific to this library:
- Include the library with #include <nlohmann/json.hpp>. The public API is nlohmann::json (nlohmann::basic_json), nlohmann::ordered_json, json_pointer, json patch/merge_patch and the documented SAX and conversion interfaces. Never use the detail namespace.
- It is a header-only library: nothing to link. Programs are compiled as C++17.
- Print JSON values with dump() (compact) or dump(2). Keys of nlohmann::json objects print in sorted order, so output is deterministic; do not depend on insertion order except with ordered_json.

# Pull request #5805: Fix silent wrong results for custom number types

## Description
Two silent wrong-result bugs for custom number types that already compile on `develop`, found while analysing #3578.

## Integer/float comparison with a class-type integer

`compare_integer_with_float()` (`detail/value_t.hpp`) took the signedness from `std::is_signed<IntegerType>`, which is `false` for class types such as `absl::int128` or `boost::multiprecision::cpp_int`. Every float below zero then compared as less than every integer:

```cpp
using J = nlohmann::basic_json<std::map, std::vector, std::string, bool, absl::int128, absl::uint128, double>;
J i(J::value_t::number_integer);
i.get_ref<absl::int128&>() = -5;
J(-2.5) < i;  // true before, false now
i < J(-2.5);  // false before, true now
```

The signedness now comes from `std::numeric_limits<IntegerType>::is_signed`, matching the `digits` already used for the range bound.

## Binary writers with integer types wider than 64 bits

With `basic_json<..., __int128, unsigned __int128, double>`:

| format | before | after |
|---|---|---|
| CBOR | truncated (2^100 → 0) | `out_of_range.407` outside [-2^64, 2^64-1] |
| MessagePack | truncated | `out_of_range.407` outside [-2^63, 2^64-1] |
| BSON | truncated | `out_of_range.407` outside int64 (signed) / uint64 (unsigned), before anything is written |
| BON8 | did not compile (`std::to_string` ambiguous) | `out_of_range.407` outside int64 (same message as before for uint64) |
| UBJSON | exact `H` high-precision number | unchanged |
| BJData | signed: exact `H`; unsigned: truncated via `M` | unsigned beyond uint64 also written as `H` |
| BJData ND-array | elements/dimensions beyond 64 bits truncated before the range check, so they could be encoded as wrong values | object falls back to a plain object, like other out-of-range elements |

The checks (`integer_fits_max/min/fits` in `binary_writer`) get the ranges from `std::numeric_limits` digits. They dispatch on a compile-time tag, so for number types of at most 64 bits they are the constant `true` and compile away. I checked this by compiling `to_cbor`/`to_msgpack`/`to_bson`/`to_ubjson`/`to_bjdata`/`to_bon8` for the default `json` at -O2. The CBOR, MessagePack and BSON writer functions have identical instruction counts before and after (clang). The UBJSON/BJData functions change by a few instructions because clang now makes different inlining decisions; they get no extra runtime checks. The cold throw path is shared with BON8.

The error message prints the number with `dump()`, because `std::to_string` has no overload for `__int128`.

## Tests

New file `tests/src/unit-custom-number-types.cpp`:
- A small trivial class-type signed integer with `std::numeric_limits` specialized (`is_signed = true`), standing in for `absl::int128`, which CI does not have. It covers `<`, `>`, `<=`, `>=`, `==`, `!=` against floats, including floats outside the integer's range.
- `__int128`/`unsigned __int128` writers for all formats, including the edges of each range and the ND-array fallback. These tests are compiled only when the standard library treats `__int128` as an integral type: libc++, or libstdc++ outside strict ISO mode (`__GLIBCXX_TYPE_INT_N_0`; CMake builds use GNU mode by default). A `static_assert` checks the traits.

Against `develop`'s headers, 30 of the new assertions fail (BON8 part left out, since it doesn't compile there). With the fix, all pass with Apple clang, GCC 16 and GCC 9 (C++11/17/20). Also checked: the existing cbor/msgpack/bson/ubjson/bjdata/bon8/comparison/binary_formats suites under ASan/UBSan, GCC 16's CI warning flags, clang `-Weverything` (Apple clang and clang 19), and clang-tidy with the repo config.

Docs: the `out_of_range.407` entry in `exceptions.md` (it still said the exception could not occur, although BON8 already throws it) and the exception sections and version histories of `to_cbor`, `to_msgpack`, `to_bson`, `to_bjdata` and `to_bon8`.

{
    // contiguous input derives the position from the input on error, stream
    // input counts it while reading (see lexer::lazy_position); the cases
    // cover newlines before the error, ungetting a newline after a number,
    // newlines inside a string, a comment, and reads at the end of input
    struct test_case
    {
        std::string input;
        std::size_t byte;
        std::string message;
    };
    const std::vector<test_case> cases =
    {
        {"[\n  1,\n  2\n", 12, "[json.exception.parse_error.101] parse error at line 4, column 1: syntax error while parsing array - unexpected end of input; expected ']'"},
        {"[1\n,2,\n]", 8, "[json.exception.parse_error.101] parse error at line 3, column 1: syntax error while parsing value - unexpected ']'; expected '[', '{', or a literal"},
        {"[1\n x]", 5, "[json.exception.parse_error.101] parse error at line 2, column 2: syntax error while parsing array - invalid literal; last read: '1<U+000A> x'; expected ']'"},
        {"1\n2", 3, "[json.exception.parse_error.101] parse error at line 2, column 1: syntax error while parsing value - unexpected number literal; expected end of input"},
        {
            "{\"a\":\n\"b\nc\"}", 9, R"([json.exception.parse_error.101] parse error at line 3, column 0: syntax error while parsing value - invalid string: control character U+000A (LF) must be escaped to \u000A or \n; last read: '"b<U+000A>')"
        },
        {"/* a\n b */\n x", 13, "[json.exception.parse_error.101] parse error at line 3, column 2: syntax error while parsing value - invalid literal; last read: '/* a<U+000A> b */<U+000A> x'"},
        {"\n\n", 3, "[json.exception.parse_error.101] parse error at line 3, column 1: syntax error while parsing value - unexpected end of input; expected '[', '{', or a literal"},
        {"[\"a\",\n 1e\n]", 10, "[json.exception.parse_error.101] parse error at line 3, column 0: syntax error while parsing value - invalid number; expected '+', '-', or digit after exponent; last read: '1e<U+000A>'"},
        {"[tru\n]", 5, "[json.exception.parse_error.101] parse error at line 2, column 0: syntax error while parsing value - invalid literal; last read: '[tru<U+000A>'"},
    };

    for (const auto& c : cases)
    {
        CAPTURE(c.input)
        const std::string expected = std::to_string(c.byte) + " " + c.message;

        SaxErrorRecorder string_sax;
        CHECK_FALSE(json::sax_parse(c.input, &string_sax, json::input_format_t::json, true, true));
        CHECK(string_sax.error == expected);

        SaxErrorRecorder pointer_sax;

        std::istringstream is(c.input);
        SaxErrorRecorder stream_sax;
        CHECK_FALSE(json::sax_parse(is, &stream_sax, json::input_format_t::json, true, true));
        CHECK(stream_sax.error == expected);
    }
}
