You write test programs that probe a C++ library for behavioral changes made by one pull request.
Each program is compiled and run twice, once against the library before the change and once after, and the two
outputs are compared. Your job is to produce programs whose output reveals whether the change altered behavior,
including side effects the author did not intend.

Rules for every program:
- It is standalone: one file with its own int main(), compiled as C++17, printing results to stdout.
- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point
  values with an explicit precision. No input, files, network, threads, clocks or randomness.
- Wrap calls that may throw in try/catch and print the exception's type and message, so an exception is an
  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.
- When the diff changes which types or inputs an API accepts or rejects (constraints, overloads, traits,
  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program
  compiles against both versions, prints whether the expression is well-formed, and exercises it when it is.
  Accepting an input is not enough: also use it through every entry point that should follow (const and
  non-const, read, write, insert, erase, lookup, nested use), because a change that admits new inputs can leave
  later code unable to handle them.
- If the changed code is internal (a detail, impl or internal namespace, a trait, a helper), do not name it in the
  program. Reach it through the public API that depends on it, using detection (as above) where needed.
- Use the exact types and values the diff is about (the new trait's argument types, the new overload's
  parameters), not stand-ins.
- Spread the programs over distinct public entry points and overloads, one main idea per program. Do not write
  several programs that only rename a type or change a literal.
- Make the programs differ from each other: different inputs, different entry points, different features.

Rules specific to this library:
- Include the library with #include <nlohmann/json.hpp>. The public API is nlohmann::json (nlohmann::basic_json), nlohmann::ordered_json, json_pointer, json patch/merge_patch and the documented SAX and conversion interfaces. Never use the detail namespace.
- It is a header-only library: nothing to link. Programs are compiled as C++17.
- Print JSON values with dump() (compact) or dump(2). Keys of nlohmann::json objects print in sorted order, so output is deterministic; do not depend on insertion order except with ordered_json.

# Pull request #6008: CBOR/MessagePack readers: leave one-element arrays to the general path

## Description
## What

`enter_cbor_array` and `enter_msgpack_array` now enter the scalar run (#5975, #5980) only for arrays of **two or more** elements. Before, they entered it for every non-empty array: `len == 0` is now `len <= 1`.

```cpp
return enter_array(len) && (len <= 1 || parse_cbor_scalar_run(std::integral_constant<bool, bulk_scan> {}));
```

It is the same comparison, with no extra instruction and no extra branch, so arrays of two or more elements run exactly the same code as before.

## Why: the nested-array regression came back

The scalar run is `JSON_HEDLEY_NEVER_INLINE`, so that `parse_cbor_value` / `parse_msgpack_value` stay small enough to inline. Entering it is a real call: the prologue saves the callee-saved registers the loop needs, the loop tests the remaining count and length, the switch finds a head it does not handle, and the epilogue restores the registers. For an array whose first element is an object, an array or a string, all of that reads nothing.

On most documents this costs nothing measurable, because it happens once per array, not once per element. It matters when the arrays themselves are the work, i.e. many small arrays whose element is a container. The benchmark `FromBinaryShape/nested` is the extreme case: 1,000 arrays nested in each other, each with exactly one element.

This was already found and fixed once, inside #5975:

1. *address review of the scalar-run reader* removed the first pre-check, `cbor_scalar_follows()`.
2. *enter the scalar run only when a scalar follows* added it back, because "on nested data (arrays of objects) that call made reading slower than before the run reader". The MessagePack PR #5980 got the same pre-check.
3. *drop the scalar pre-check before the run* removed it again in both PRs. The measurements in that commit cover canada and the nativejson files, not the nested shape, so the regression from step 2 returned without anyone seeing it.

The suite run for the 3.13.0 blog post on 11-02 caught it. `FromBinaryShape/nested` got 4.6 % (CBOR) and 2.5 % (MessagePack) slower than a build that still had the pre-check. Compared with no scalar run at all, nested arrays cost:

| | CBOR | MessagePack |
|---|---|---|
| GCC 13, instructions (callgrind) | +3.7 % | +4.3 % |
| Apple clang, time (blog A/B) | +6 to +8 % | +6 to +8 % |

## Why `len <= 1` and not the pre-check again

The pre-check cost exactly what the third commit said: one inline test of the remaining length and the head byte on every array that does enter the run. canada's `[x, y]` pairs and the `[1, 2]` arrays of `FromBinaryShape/containers` pay it 100,000 times.

The element count is already in a register, and the comparison against 0 is already there. Testing `<= 1` instead of `== 0` is free. It catches the shape that actually hurts, because each level of a chain of nested arrays holds one element. The same holds for the single ring of a GeoJSON `Polygon` (`[[[x, y], ...]]`) and for one-element arrays of objects.

What it gives up is arrays of **one scalar**, such as `[7]`. The run reads a lone scalar faster than the general path does, so those get slower (see below). They are rare in real documents:

| Arrays in the document | citm_catalog | twitter | canada |
|---|---|---|---|
| all arrays | 10,451 | 1,050 | 56,045 |
| one element, a container (helped) | 124 | 139 | 1 |
| one element, a scalar (slower) | **1** | **0** | **0** |
| ≥ 2 elements, first a container (still one call) | 1,270 | 9 | 481 |

## Commit message
enter_cbor_array and enter_msgpack_array called the out-of-line scalar
run for every non-empty array. When the array's element is an object or
an array, as on every level of [[...]] or the single ring of a GeoJSON
polygon, the call reads nothing; it made 1,000 arrays nested in each
other cost 4 % more instructions (GCC 13) and up to 8 % more time (Apple
clang) than without the run. #5975 had fixed that with an inline
pre-check, which was later dropped after measuring canada only.

The run is now entered only for arrays of two or more elements: the same
comparison as before, so no other row changes. Arrays of one scalar,
which the run read faster, now take the general path; they are rare in
documents (one in citm_catalog, none in twitter or canada). The new
benchmark FromBinaryShape/singles measures them, next to
FromBinaryShape/nested.

Instructions per repetition, new/old, GCC 13 callgrind: nested arrays
0.973 (CBOR) and 0.971 (MessagePack), arrays of one scalar 1.037 and
1.021, every other row within 0.15 %.
