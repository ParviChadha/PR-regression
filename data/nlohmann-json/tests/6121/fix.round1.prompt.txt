# Pull request #6121: Keep only the beginning and the end of a long token for error messages

## Description
Fixes #6120.

## Problem

For error messages (`last read: '...'`), the lexer keeps the text of the token it is reading. The token start moves only at strings and numbers, so after a string or number everything that follows (whitespace, structural characters, literals) still belongs to that token. Input that cannot be read again copies it while parsing: the `std::istream` and `FILE*` adapters in their carry buffer on every buffer refill, and the lexer in `token_string` for iterator and other input. Valid input such as `1` followed by 100,000,000 newlines therefore peaked at about 225 MB for `std::istream`, `FILE*` and input iterators (3.12.0: the same), and the raw text of a long string was kept a second time next to the parsed value.

## Change

The text is only used for error messages, so it does not need to be kept in full:

- `token_text_buffer<CharType>` (in `input_adapters.hpp`, outside the `JSON_NO_IO` guard) replaces the char-only `token_carry_buffer` (now an alias of `token_text_buffer<char>`) and the lexer's `std::vector<char_type> token_string`. It keeps the first 4096 and at least the last 4112 characters of a token. When it is full and holds more than 12,320 characters, it drops the characters in between instead of growing. That happens in `make_room()`, the out-of-line path that previously reallocated, so appending a character is still one comparison and a store. The capacity never exceeds 12,320 characters.
- `get_token_string()` shows a token of more than 8192 characters as its first 4096 characters, `...`, and its last 4096 characters. For contiguous input, which rebuilds the token from positions, it copies only these two parts instead of the whole range.
- `exceptions.md` (parse_error.101) describes the shortened token.

Tokens of up to 8192 characters are shown exactly as before. Messages for longer tokens are the same for every kind of input; the test below checks this for `std::string`, `std::istream`, `FILE*` and `std::list<char>`.

## Linked issue #6120: Valid input from a stream or input iterator keeps all whitespace after a string or number in memory (token text for error messages)
### Description

For error messages ("last read: '...'"), the lexer keeps the text of the token it is reading. The token start is only moved by `reset()`, which only strings and numbers call, so after a string or number everything that follows (whitespace, structural characters, literals) still belongs to that "token" until the next string or number starts. For contiguous input this costs nothing, because the text is rebuilt from positions on error. For the other inputs it is copied while parsing:

- `std::istream` and `FILE*`: the adapters keep the token themselves; on every refill of the stream buffer the token's part of the old buffer is appended to a carry buffer ([`input_adapters.hpp`](https://github.com/nlohmann/json/blob/5bad6c518bf6663b69f505511a19c98c91f77c3a/include/nlohmann/detail/input/input_adapters.hpp), `save_token_segment()`).
- input iterators and other adapters that cannot be read again: the lexer copies every character into `token_string` ([`lexer.hpp`](https://github.com/nlohmann/json/blob/5bad6c518bf6663b69f505511a19c98c91f77c3a/include/nlohmann/detail/input/lexer.hpp), `capture_char()`).

So **valid** input with a long run of whitespace after a string or number keeps all of it in memory, and the same holds for the raw text of a long string (kept once more next to the parsed value).

The text is only used for error messages (and the `last_token` of `parse_error()` in SAX), and a message that shows several megabytes of input is not useful anyway.
