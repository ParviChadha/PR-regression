# Pull request #5585: Create a value before giving it its type

## Description
## Bug

Several functions set the type of a value before they create the string, array, object or binary value behind it. When that creation throws (for example `std::bad_alloc` from the allocator), the value is left with the new type but nothing behind it:

| Where | Effect of a failed allocation (reproduced with the throwing test allocator) |
|---|---|
| `json::binary(…)` (all four overloads) | the temporary's destructor fails `assert_invariant`, which **aborts debug builds** |
| `operator[]`, `push_back`, `emplace_back`, `emplace` and `update` on a null value | the value becomes an array or object that doesn't exist; later accesses dereference a **null pointer** |
| `to_json(j, …)` into an existing value (string, binary, array, `std::vector<bool>`, `std::valarray`, ranges, object) | the old value is destroyed first, so `j` keeps a pointer to it; the value is then used and freed again (**heap-use-after-free** under ASan) |

The constructors themselves were never affected: a partially constructed value is cleaned up by `data`'s destructor, which tolerates the null pointer.

## Fix

- **`json.hpp`:** the value is created first and the type is set afterwards. The two statements are swapped at 15 places.
- **`to_json.hpp`:** each external constructor first creates the new `json_value` (or the complete `array_t` for `std::vector<bool>`, `std::valarray` and ranges), then destroys the old value and takes the new one. A comment at the top of the file explains the order.

A failed allocation now leaves the value unchanged.

## Tests

A new test case in `unit-allocator.cpp` makes the allocator fail for each of the paths above, and checks that the value is unchanged afterwards.

Against `develop`, the three sections fail as follows:
- an assertion abort;
- a `CHECK(j.is_null())` failure, followed by a `type_error.305`;
- an ASan heap-use-after-free.

With this change, the test passes under ASan and UBSan. I also ran the conversion, constructor, UDT, diagnostics and element-access suites against the amalgamated header.

## Breaking changes

None. Behavior only differs after a failed allocation, where the value now stays unchanged instead of becoming invalid.
