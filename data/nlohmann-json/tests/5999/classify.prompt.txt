# Pull request #5999: json_view: dump() without StringType::capacity()

## Description
Fixes #5994.

## What

`output_buffer::grow()` in `detail/view/serializer.hpp` compared the output size with `m_out.capacity()` to decide how far a growth step may go and whether to `reserve()`. `capacity()` is not part of the StringType requirements, so `basic_json_view::dump()` did not compile with the tests' `alt_string`.

The buffer now remembers what it last passed to `reserve()` (`m_reserved`, initialized to the estimate). That is a lower bound of the real capacity, so the growth steps behave as before; at worst a `reserve()` is issued that the string would not have needed, which is then a no-op.

## Docs

`template_parameters.md`, StringType "Required for other functionality": `basic_json_view::dump` needs `reserve(n)` and `resize(n)` (one argument); `capacity()` is not required.

## Tests

`unit-alt-string.cpp`, new test case "alternative string type with json_view": a read-only document over `alt_json` (dump plain, indented, ensure_ascii, against `alt_json::dump()`; materialize; `contains`/`operator[]` with `alt_string` keys), a dump large enough for several growth steps, and an editable document (`set`, `push_back`, `save()`/`load()`). Without the fix, the file does not compile (`no member named 'capacity' in 'alt_string'`); with it, it passes under C++11 and C++17 (Apple clang).

## Public API

No breaking changes.

### Description

`basic_json_view::dump()` (json_view, merged 2026-10-21) does not compile with a `StringType` that satisfies the documented StringType requirements but has no `capacity()` member. The library's own reference for the minimal `StringType` is the `alt_string` class in `tests/src/unit-alt-string.cpp`: `basic_json<std::map, std::vector, alt_string>` compiles and passes its unit test, but `basic_json_document<...>::parse(...)` followed by `root().dump()` fails with

## Discussion before merge
- nlohmann: ### Performance check

**No performance impact.** `output_buffer::grow()` now tracks the reserved size in a member instead of calling `capacity()`. `grow()` only runs when the size estimate is exceeded, so this is a cold path.

- **Generated code** (clang, arm64): two functions differ. `output_buffer::grow()` is **one 16-byte block shorter**, because it no longer decodes libc++'s short-string capacity. The `dump()` entry stores the new member, which is one or two instructions per `dump()` call. Everything else is identical.
- **Instruction counts**: all 38 rows are within ±0.4 %. The view `dump()` rows (twitter 1.0001, citm_catalog 1.0005, canada 1.0006, ensure_ascii twitter 1.0008) sit inside the noise band. The rows with identical code move by the same +0.05–0.1 %.
- With the default `std::string`, growth is the same up to allocator rounding. `m_reserved` is the last size passed to `reserve()`, so it never exceeds `capacity()`. Doubling now starts from the requested size instead of the rounded capacity. If the caller passes a string that already has more capacity, the extra `reserve()` is a no-op, so the number of reallocations does not grow.

- nlohmann: @gregmarr Right, before C++20 a `reserve(n)` below `capacity()` is allowed to act as a shrink request, so "a no-op" in the description is stronger than the standard promises. I checked the two libraries I can run: libc++ (C++11 and C++17) and libstdc++ 16 (C++11, C++17 and C++20) leave the capacity alone in all of these cases (`reserve` below the capacity, and after a `resize`), so I don't expect any implementation to shrink either; MSVC's STL I could not test.

It could only matter when the caller's string already has a capacity above `m_reserved`. There, a library that did shrink would reallocate to a size that is still at least what `grow()` needs, so the result stays correct and only costs one copy. The `out.reserve(estimate)` in `start()` has had the same exposure all along, and the old `capacity()` check was the only thing that avoided it in `grow()`. Avoiding it entirely would need a detected `capacity()`, which I think is more machinery than it is worth. Do you see it differently?
