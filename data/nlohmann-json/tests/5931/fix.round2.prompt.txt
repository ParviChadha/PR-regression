# Pull request #5931: Read BJData ND-arrays of float16, restrict ND-array char to 0..127, correct BJData docs

## Description
## Summary
- Reading an ND-array with element type `h` (`[$h#[$U#U 2 2 …`) threw `parse_error.112` with a misleading byte; it is now read (`_ArrayType_: "half"`). The writer still does not pack `half` (a plain object that reads back equal). Verified against numpy float16 for all 65536 bit patterns and pybj.
- BJData Draft 2 and 3 limit `C` to 0..127. ND-arrays with `_ArrayType_: "char"` wrote and accepted larger values. The writer now packs only 0..127 (other data falls back to a plain object that round-trips equal); the reader rejects `C` > 127 with `parse_error.113`, like the 1-D reader.
- Docs: unused markers, ND example (3×2), ND packing conditions, `byte`/binary rules, `H`, supported drafts, Draft 4 and column-major as unsupported, duplicate keys, Draft-3 links, `$` requires `#`, new `bjdata_version_t` API page with example, `parse_error.115`, `out_of_range.408`, `other_error.502`, binary values pages.

## Breaking changes
No API or ABI change. Two edge-case behaviour changes: ND-arrays of `h` can now be read (they threw before); ND `char` data above 127 is no longer written as packed `C` (a plain object is written instead), and a packed ND `C` array containing a byte above 127 is now rejected with `parse_error.113` instead of being returned. Such streams are invalid under both drafts and rejected by pybj, but a stream written by an earlier version of this library could contain them.

Not covered: column-major ND-arrays, packing `half`, Draft 4.

## Stack
This PR is part of a stack of six PRs from a review of the binary formats against their specifications and other implementations (CBOR → MessagePack → UBJSON → BSON → BJData → BON8). Please merge in that order.

## Commit message
* Read ND-arrays of half floats and enforce the char limit in ND-arrays

BJData N-dimensional arrays with element type 'h' (float16) failed to
read with a misleading parse_error.112, because the reader's dtype name
table lacked 'h'. It now maps to "half", the JData name. The writer still
does not pack "half"; such an object is written as a plain object and
reads back equal.

BJData limits 'C' (char) to 0..127 in Draft 2 and Draft 3, and the 1-D
reader enforces this, but ND-arrays with _ArrayType_ "char" wrote values
up to 255 as 'C' elements and read them back without a check. The writer
now only packs values in 0..127 (others fall back to a plain object that
round-trips), and the reader rejects 'C' elements above 127 with
parse_error.113 like the 1-D reader.
