Each program is compiled and run twice, once against the library before the change and once after, and the two

Rules for every program:

- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point

  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.

  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program

# Pull request #5797: Make UTF8_ACCEPT/UTF8_REJECT inline variables to avoid TU-local exposure in modules

## Description
Fixes a module export error with GCC 15.2 when nlohmann/json is included in the global module fragment of a C++ module and exported (-std=c++23).

detail::UTF8_ACCEPT and detail::UTF8_REJECT in detail/string_utils.hpp are `static constexpr` at namespace scope, so they have internal linkage.

```
string_utils.hpp:199:13: error: 'template<class StringType> bool
nlohmann::json_abi_v3_12_0::detail::is_valid_utf8(const StringType&, std::size_t)'
exposes TU-local entity 'nlohmann::json_abi_v3_12_0::detail::UTF8_ACCEPT'
string_utils.hpp:111:31: note: 'nlohmann::json_abi_v3_12_0::detail::UTF8_ACCEPT'
declared with internal linkage
  111 | static constexpr std::uint8_t UTF8_ACCEPT = 0;
```

Change: use JSON_INLINE_VARIABLE, which already exists for static_const::value:

    JSON_INLINE_VARIABLE constexpr std::uint8_t UTF8_ACCEPT = 0;
    JSON_INLINE_VARIABLE constexpr std::uint8_t UTF8_REJECT = 1;

In C++17 and later this is `inline constexpr` (external linkage, one definition), which works with modules. Before C++17 the macro expands to nothing, so the declaration stays plain `constexpr` (still internal linkage there, as before). No behavior change for C++11/14.
