# Pull request #5822: Escape characters below 0x60 from a table straight into the write buffer

## Description
## What

When the bulk scanner in `dump_escaped_impl()` stops at a control character, a quote or a backslash, that byte went through the UTF-8 decoder and a `switch` that wrote the escape byte by byte into `string_buffer`. The buffer was then copied into `write_buffer` at the next unescaped run.

A byte below 0x60 at a character boundary is a complete code point, so it now skips the decoder. Its escape sequence comes from a 96-entry table with 8-byte rows: the sequence is padded with zeros, and the last byte holds its length. All 8 bytes are copied straight into `write_buffer` after one room check, and the position advances by the length. The idea comes from orjson's `QUOTE_TAB`. Most of the gain comes from skipping the `string_buffer` round trip, not from the table. A table-only variant that still went through `string_buffer` gained only 2–7 %.

The check sits inside the existing character-boundary block, so it runs once each time the scanner stops, not once per byte. A first version tested every byte and cost about 6 % on twitter.json with `ensure_ascii`, where every byte of a CJK character went through the extra comparison.

The `switch` in the decoder's accept branch lost its cases for characters below 0x60, which can no longer reach it. What is left is "\u-escape under `ensure_ascii`, else copy the byte".

Changes:
- `detail/output/serializer.hpp`: the table (`ascii_escapes()`), the direct write in `dump_escaped_impl()`, and the smaller accept branch.
- `tests/src/unit-serialization.cpp`: new test case and updated string-buffer boundary tests (see below).

This allows you to put more bytes into the buffer without flushing, and copies fewer bytes.
- gregmarr: Have you considered putting the size first and then you don't need to pad with trailing zeros in the initializers when you're not using all the bytes?
- nlohmann: The `memcpy` deliberately copies all 8 bytes: with a constant size it compiles to one 64-bit load/store, whereas a variable-size copy becomes a call or a branch cascade. So the room check has to cover 8 bytes, not `escape[7]` — checking only `escape[7]` while copying 8 could write past the end of `write_buffer`. One could add 7 bytes of slack to the buffer and check the real length, but that only saves an occasional flush a few bytes early once per 1 KiB, which doesn't change the output and isn't measurable. I'd keep it as is.

- nlohmann: Then the sequence starts at offset 1, and an 8-byte copy from `data() + 1` would read into the next entry (and past the array for 0x5F). The options are a 7-byte copy (two stores instead of one) or 9-byte entries (losing alignment). The trailing zeros are only how the table looks in the source and cost nothing at runtime, so I'd rather keep the single aligned store.

TEST_CASE("serializer buffers are flushed mid-string and mid-binary")

    {

        std::string expected = "\"";
        for (int i = 0; i < 600; ++i)

            expected += "\\n";

        std::string escaped_umlauts = "\"";
        for (int i = 0; i < 300; ++i)

        }
        escaped_umlauts += '"';
        CHECK(json(umlauts).dump(-1, ' ', true) == escaped_umlauts);
    }

    SECTION("a large binary value")
    {
        std::vector<std::uint8_t> bytes(3000);
