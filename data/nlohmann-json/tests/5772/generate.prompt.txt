# Pull request #5772: Make std::hash<basic_json> consistent with operator== for numbers

## Description
Closes #5400.
Closes #5256.

`std::hash<basic_json>` gave different hashes to numbers that compare equal (`json(0)`, `json(0U)`, `json(0.0)`), so a `std::unordered_set<json>` could hold all three. That breaks the requirement that `a == b` implies `hash(a) == hash(b)`.

This continues #5447 by @afonsojanu, who closed it on 10-05 to start fresh. Their three commits are cherry-picked unchanged (authorship kept), so the credit for the fix is theirs. It also supersedes my earlier attempt #5262.

### Changes

- **Fix (@afonsojanu):** `hash()` hashes every number as its `number_float_t` value under one shared type tag. Since #5459, `operator==` compares numbers by exact mathematical value. Two equal numbers therefore have the same value and convert to the same `number_float_t`, so they hash equally, including at the range ends. The tests now check this consistency, including through an `unordered_set`. The docs no longer describe the old behavior as intended.
- **Follow-up:**
  - Maps `-0.0` to `0.0` before hashing, because `-0.0 == 0` and `std::hash` is not required to treat them alike.
  - Updates the code comment to say exact comparison instead of "converts before comparing".
  - Tests `-0.0`, `INT64_MIN`, 2^63 as unsigned, and `INT64_MAX` stored as unsigned.
  - Adds `hash(0.0)` to the docs example, regenerates its output, adds a version-history note, and re-amalgamates.

Unequal but nearby large integers (for example 2^53 and 2^53+1) now share a hash. That is allowed, and such collisions are rare in practice.

### Breaking changes

There is no API or ABI change. Hash *values* change for every number, and for every container that holds one. Code that relied on `0`, `0U` and `0.0` hashing differently, or that persisted hash values, will see different results. Hash values were never stable across platforms or versions.

## Linked issue #5400: std::hash<basic_json> is inconsistent with operator== for equal cross-type numbers (breaks unordered containers)
### Description

`std::hash<basic_json>` can produce **different** hash values for two `json` values that compare **equal** under `operator==`. The C++ standard requires of a `Hash` used with `std::unordered_map`/`unordered_set` that `a == b` implies `hash(a) == hash(b)`; this invariant is violated for numbers of different internal types.

`operator==` converts between `number_integer`, `number_unsigned`, and `number_float` before comparing ([`include/nlohmann/json.hpp`](https://github.com/nlohmann/json/blob/develop/include/nlohmann/json.hpp), `JSON_IMPLEMENT_OPERATOR`), so `json(0) == json(0.0) == json(0u)` are all `true`. But `hash()` folds the `value_t` type tag into the result via `combine(type, h)` ([`include/nlohmann/detail/hash.hpp`](https://github.com/nlohmann/json/blob/develop/include/nlohmann/detail/hash.hpp)), giving each of the three a distinct hash.

Consequently a `std::unordered_set<json>` can hold `json(0)`, `json(0.0)`, and `json(0u)` as three separate elements even though they are all equal — silent duplicate keys / lookup misses.

The documentation ([`std_hash.md`](https://github.com/nlohmann/json/blob/develop/docs/mkdocs/docs/api/basic_json/std_hash.md)) currently describes this as intended ("different hash values for `null`, `0`, `0U`, and `false`"). But `0`, `0U`, and `0.0` are *equal* under `operator==`, so distinguishing them by hash is precisely the contract violation. Only `false` vs `0` is legitimately distinguishable (those are not equal — different `value_t` and no cross-conversion). This looks like a case where the documented intent itself encodes the bug.

### Reproduction steps

Hash `json(0)`, `json(0.0)`, `json(0u)`; observe they are `==` but hash differently and coexist in an `unordered_set`.

### Expected vs. actual results

- **Expected:** equal values hash equally; `unordered_set` of `{0, 0.0, 0u}` has size 1.
- **Actual:** three distinct hashes; `unordered_set` size is 3.

## Linked issue #5256: Int and uint compare equal but hashes do not
### Description

On the implementation of `std::hash`, [the C++ specification](https://en.cppreference.com/cpp/utility/hash) states:

> If `k1 == k2` is `true`, `h(k1) == h(k2)` is also `true`

Yet this is not the case for `json` values of the same numeric value but of signed and unsigned storage types. I can see this behaviour is documented [here](https://json.nlohmann.me/api/basic_json/std_hash/), but it violates the `std::hash` contract. While this behaviour is great for distinguishing between the other types, it feels unnatural for it to distinguish between signed and unsigned types.

### Reproduction steps

```C++
using namespace nlohmann;

int main()
{
    const json a{42};
    const json b{42u};

    assert(a == b);
    assert(std::hash<json>{}(a) == std::hash<json>{}(b));
}
```

### Expected vs. actual results

I would expect `assert(std::hash<json>{}(a) == std::hash<json>{}(b));` to succeed because `a == b` is `true`, but it actually fails.

I believe the `hash<basic_json>` implementation should treat signed and unsigned integers the same. This is especially important because the storage type selected by the parser is not specified (currently, see #5255 ).

In all other aspects, signed and unsigned integers are treated the same: there is no distinction made in the JSON standard and they are silently cast between when calling `.at()` or `.get<>()`.

    std::cout << m.at(j.at("a")) << '\n'; // throws std::out_of_range
