# Pull request #5782: Use MSVC intrinsics for full multiplication

## Description
`full_multiplication()` currently uses `unsigned __int128` on GCC/Clang and falls back to four 32-bit partial products everywhere else. This adds the native intrinsics for the two MSVC targets that have them.

- **x64:** `_umul128(a, b, &high)` gives both halves of the 128-bit product.
- **ARM64:** `a * b` provides the low half and `__umulh(a, b)` provides the high half.
- `<intrin.h>` is included only for MSVC x64/ARM64 builds, so other compilers and platforms are unaffected.
- The `__SIZEOF_INT128__` branch remains first. This is important for clang-cl, which defines that macro and should continue using `unsigned __int128`.
- 32-bit MSVC and other compilers continue to use the existing portable fallback unchanged.

I extended the existing "128-bit products and leading zeros" test section with fixed edge cases checked against the existing big-integer reference, including `0`, `1`, `UINT64_MAX`, values around `2^32`, and large boundary values. The existing deterministic random-pair coverage is also preserved.

`single_include/nlohmann/json.hpp` is synchronized with the implementation change.

**Testing:** the touched tests pass locally with ASan and UBSan, and `git diff --check` is clean. MSVC/clang-cl are not available in my local environment, so the new MSVC branches have not been compiled locally. The repository's Windows CI jobs should provide compiler-specific validation.

**Performance:** I have not benchmarked this change. The goal is to use the native 64×64-bit multiplication support provided by MSVC rather than the portable partial-product implementation.

Closes #5780

## Linked issue #5780: Use MSVC intrinsics for the 64×64-bit multiplication in full_multiplication()
`detail::full_multiplication()` in `include/nlohmann/detail/bit_ops.hpp` (added in #5617) computes the 128-bit product of two 64-bit numbers. GCC and Clang use `unsigned __int128`. All other compilers, including MSVC, fall back to four 32-bit partial products. MSVC has intrinsics for this:

- x64: `_umul128(a, b, &high)` returns the low half and stores the high half (`<intrin.h>`).
- ARM64: `a * b` for the low half and `__umulh(a, b)` for the high half.

## Proposal

Add an `#elif defined(_MSC_VER) && (defined(_M_X64) || defined(_M_ARM64))` branch to `full_multiplication()` and keep the portable fallback for everything else (32-bit MSVC, other compilers). `clang-cl` defines `__SIZEOF_INT128__` and takes the first branch, so the order of the branches matters. Add a unit test that compares the result with the portable formula for edge values: 0, 1, `UINT64_MAX`, values around 2^32, and a few random pairs.

## Why now, and why not yet

- **On `develop`, MSVC gains little.** The only caller is the Eisel–Lemire fallback in `number_parse.hpp`, which is only used when `std::from_chars` for floating-point is unavailable. Current MSVC has it.
- **With the zero-copy view stack (#5768) it matters.** #5634 writes doubles with Żmij (`detail/conversions/zmij.hpp`), which calls `full_multiplication()` several times per number, and #5738 parses floats with it. MSVC would then run the slow fallback in the hot path of `dump()` for every double.

So this is worth doing once that stack is merged (or with it), and should be measured on MSVC x64 with `dump()` of a float-heavy file such as canada.json.

## Background

Discussion #3782 asked for intrinsics in Grisu2's `diyfp::mul()` in `to_chars.hpp`, which uses the same 32-bit partial products. After #5634, Grisu2 is only used for `float`, so changing `diyfp::mul()` is not worth it on its own. It could call `full_multiplication()` to remove the duplicate code, keeping its rounding of the low half.
