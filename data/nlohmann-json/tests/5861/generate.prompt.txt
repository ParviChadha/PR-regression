Each program is compiled and run twice, once against the library before the change and once after, and the two
outputs are compared. Your job is to produce programs whose output reveals whether the change altered behavior,
including side effects the author did not intend.

Rules for every program:
- It is standalone: one file with its own int main(), compiled as C++17, printing results to stdout.
- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point
  values with an explicit precision. No input, files, network, threads, clocks or randomness.
- Wrap calls that may throw in try/catch and print the exception's type and message, so an exception is an
  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.
- When the diff changes which types or inputs an API accepts or rejects (constraints, overloads, traits,
  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program

  Accepting an input is not enough: also use it through every entry point that should follow (const and

# Pull request #5861: Speed up flatten(), unflatten(), diff() and patch()

## Description
`flatten()`, `unflatten()` and `diff()` spent most of their time on work that can be avoided: searching a `std::map` from the root for every flattened path, splitting every key into a vector of strings and walking it from the root again, and building every diff operation from initializer lists. This makes them 1.4× to 2.3× as fast, and `patch()` a little faster. Output, exceptions and the state left after a failing patch are unchanged.

One commit per change:

1. **flatten:** for object types with `emplace_hint` (`std::map`), each path is inserted next to the entry added last, since paths come out in nearly sorted order. `ordered_map` keeps its append without lookup; other object types keep `operator[]`. Path segments are appended in place.
2. **unflatten:** keys are checked by a scan that throws the same `parse_error.107`/`108` as `split()`, skipping the part shared with the previous key. The prefixes that become arrays are kept in a small hash set of key slices instead of a prefix tree, and the walk keeps the values along the previous key's path, so only the part of a key that differs from the previous one is looked up. The array/object decision is unchanged.
3. **patch:** `add`, `remove`, `replace` and `test` on a path without escapes that denotes existing values (as `diff()` creates them) are applied without building a `json_pointer`. Everything else, and every operation that would fail, takes the existing code.
4. **diff:** operations are built member by member instead of from initializer lists (about 25 allocations each before), and paths are built in place.
5. **diff:** objects with the same keys in the same order are walked together without lookups, and the path is one buffer that is extended and shortened again.

std::map of the result searched the tree from the root and compared long

operator[].

unchanged.

    const ordered_json original = make_rich_ordered_json();

    const std::vector<std::string> original_mango_keys = collect_keys(original["mango"]);

    CHECK(collect_keys(unflattened) == original_keys);
