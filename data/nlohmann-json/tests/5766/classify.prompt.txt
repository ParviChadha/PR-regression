# Pull request #5766: Reject nested indefinite-length CBOR string chunks

## Description
Closes #5317. Supersedes #5325 by @JosephDemarest. Their commit is kept with their authorship; this PR rebases it onto the current `develop` and adds the remaining review points.

RFC 8949 §3.2.3 doesn't allow indefinite-length strings to be nested. Until now, the CBOR reader accepted nested indefinite-length text and byte strings (it counted the open levels instead of recursing; see #5104). With this change it rejects them at the nested marker with `parse_error.113`. The reader stays iterative.

## Changes

- **54beb8ffa** (JosephDemarest, rebased): reject a second `0x7F`/`0x5F` inside an indefinite-length string, list only the definite-length forms in chunk error messages, keep the byte-for-byte decoding check for the valid prefix of `cbor_binary.cbor`, and add regression tests.
  - Conflict resolution: `exception_message()` no longer takes the input format. Also, the break marker that closes an indefinite-length text string now runs `check_string_utf8()` again, as it does on `develop` since #5741. A plain auto-merge had silently dropped that check; the existing "ill-formed UTF-8 in indefinite-length string" test covers it.
- **65bcce35b**: review nits from #5325: rename `is_chunk` → `inside_indefinite`, update the stale test section names, use lowercase comments.

## Public API

No signatures change, but the behavior does: nested indefinite-length CBOR strings or byte arrays that used to parse now throw `parse_error.113` (or return a discarded value if exceptions are disabled). Valid definite- and indefinite-length strings work as before. This will go in the release notes.

## Linked issue #5317: CBOR: nested indefinite-length strings/byte strings are accepted (RFC 8949 3.2.3 requires definite-length chunks)
### Description

RFC 8949 §3.2.3 requires that the chunks of an indefinite-length string be *definite-length* strings of the same major type:

> Each chunk of an indefinite-length string is a definite-length string of the same major type.

`get_cbor_string()` and `get_cbor_binary()` read each chunk by recursing into themselves ([`binary_reader.hpp:1025-1037`](https://github.com/nlohmann/json/blob/8ec98e2c9ea9c0adc15a791feb3d4d4468621743/include/nlohmann/detail/input/binary_reader.hpp#L1025-L1037) and [`1125-1137`](https://github.com/nlohmann/json/blob/8ec98e2c9ea9c0adc15a791feb3d4d4468621743/include/nlohmann/detail/input/binary_reader.hpp#L1125-L1137)), and the recursive call re-enters the full `switch` including the `0x7F`/`0x5F` case. So a chunk may itself be an indefinite-length string, to arbitrary depth, and the library accepts it.

The cross-major-type rule is already enforced correctly — a byte-string chunk inside a text string is rejected, and vice versa. It is only the "definite-length" half of the rule that is missing.

Secondary effect: because the nesting is unbounded, `0x7F` repeated ~50 000 times segfaults. That aspect overlaps with #5104 / #5293, but a depth guard alone would only turn the crash into a clean `parse_error` — the two-level case below would still be accepted rather than rejected. The conformance fix is independent and cheaper: reject `0x7F`/`0x5F` when already inside an indefinite-length string, which also removes this particular recursion path entirely.

### Reproduction steps

Parse a two-level indefinite-length text string and byte string.

### Expected vs. actual results

Expected: `parse_error.113`, same as any other invalid chunk head.

Actual:

| input | meaning | result |

| `7F 7F 61 61 FF FF` | indefinite tstr containing an indefinite tstr | **accepted**, yields `"a"` |
| `5F 5F 41 61 FF FF` | indefinite bstr containing an indefinite bstr | **accepted**, yields `h'61'` |
| `7F 41 61 FF` | bstr chunk inside a tstr |

## Discussion before merge
- gregmarr: Is this a behavior change that needs an opt-in?  It sounds like they were successfully read before even though they aren't allowed by the standard.
- nlohmann: @gregmarr Good question. Yes, every release so far has accepted them, but I don't think this needs an opt-in:

- The input is not well-formed CBOR, not just discouraged. RFC 8949 §3.2.3 requires each chunk of an indefinite-length string to be a definite-length string, and Appendix F.1 explicitly lists `5f 5f 41 00 ff ff` and `7f 7f 61 00 ff ff` ("indefinite-length string chunks not definite length") as examples of data items that are not well-formed. §10 says a CBOR decoder, by definition, only accepts well-formed CBOR.
- No conforming encoder can produce such input, and our own `to_cbor` never emits indefinite-length strings at all. So the only data affected is hand-crafted or broken input.
- Accepting it was never a design decision. It was a side effect of the old reader recursing into itself for every chunk, which is also why repeated `0x7F` bytes crashed it (#5104).

That's different from cases like #5741, where real-world producers do emit the data (invalid UTF-8) and we kept the readers lenient. We'll document the change in the release notes as a behavior change: nested indefinite-length strings now throw `parse_error.113`.
