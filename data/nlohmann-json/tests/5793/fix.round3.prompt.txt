# Pull request #5793: Unflatten in time and memory linear in the pointer depth

## Description
> Stacked on #5792. Review and merge that one first; this PR's diff is just the last commit.

## Problem

Since #5443 (c72f37a40, not in any release yet), `unflatten()` takes time and memory quadratic in the depth of a pointer. To decide between arrays and objects independently of iteration order, it collects the prefixes that have a reference token `0` below them in a `std::set<std::vector<string_t>>`:

- each `0` token inserts a copy of the whole prefix so far, so an array chain of depth d stores about d²/2 strings
- `get_and_create()` pushes onto a prefix vector and looks it up in the set at every step, comparing whole vectors

On `develop`, unflattening `{"/0/0/…/0": 1}`:

| depth | time | peak RSS |
|---|---|---|
| 1,000 | 125 ms | 16 MB |
| 10,000 | 17.9 s | 1.28 GB |
| 100,000 | killed after 86 s at 6 GB | |

#5393 had confirmed that `unflatten()` handled a 500,000-level pointer before #5443.

## Change

The prefixes are now numbered nodes of a tree (`prefix_tree`): `children[id]` maps a token to the id of the extended prefix, and `is_array[id]` records whether a `0` token appears directly below it. The first pass of `unflatten()` builds the tree, storing each prefix once. `get_and_create()` then follows it token by token instead of building and comparing prefix vectors. The rule from #5443 is unchanged: a value becomes an array exactly when some key has a `0` directly below it, regardless of iteration order.

## Benchmark

Deep pointer, `unflatten()` only, `-O2`, Apple clang 21, arm64:

| depth | kind | before | after |
|---|---|---|---|
| 10,000 | arrays | 17.9 s / 1.28 GB | 1.9 ms / 3.9 MB |
| 100,000 | arrays | did not finish | 12.9 ms / 24.7 MB |
| 100,000 | objects | 6.8 ms / 21.6 MB | 10.8 ms / 31.2 MB |

Object chains weren't quadratic before (no `0` tokens), so the tree adds a small constant cost there.

Ordinary documents, best-of-7, median of 3 alternating runs (`dump()` output identical in every case):

| input | type | new/old |
|---|---|---|
| wide, 1.3 MB, 82,503 entries | `json` | 1.01 |
| wide | `ordered_json` | 1.07 |
| nested, depth 7, 100,374 leaves | `json` | 0.65 |
| nested | `ordered_json` | 0.64 |

The wide cases are within the noise of this benchmark (runs varied by up to ±25%). Wide `ordered_json` may be slower by about 5%.

## Tests

- The 100,000-level test from #5792 now round-trips through `unflatten()` at full depth; it was limited to 500 levels before.
- New: unflattening a single 100,000-level array pointer and a 100,000-level object pointer, checked by walking the result.
- New: order independence with `ordered_json`, where a `0` key comes after its sibling (`{"/a/1": 2, "/a/0": 1}` → `{"a": [1, 2]}`) and a prefix without a `0` key (`{"/b/1": 2}` → `{"b": {"1": 2}}`). The existing tests used `json`, whose sorted keys never put `0` second.

Locally: `test-json_pointer` (C++11, C++20), `test-json_patch`, `test-alt-string`, `test-custom-array-type`, `test-custom-object-type`, `test-diagnostics` and `test-ordered_json2` pass, and the build shows no warnings.

## Public API

No breaking changes. Only private members of `json_pointer` change (`array_parents_t` → `prefix_tree`, and the parameter of `get_and_create`), and the output of `unflatten()` is identical.

    const std::vector<std::string> original_mango_keys = collect_keys(original["mango"]);
