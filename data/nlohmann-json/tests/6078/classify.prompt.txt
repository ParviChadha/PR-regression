# Pull request #6078: Bound the total number of valueless UBJSON elements per input

## Description
An optimized UBJSON array of type `Z`, `T` or `F` has no payload, so its declared count is not bounded by the input. The limit of 1,048,576 applied to each array on its own, so 9 bytes (`[$Z#l` and a count) produced 1,048,576 values and every further 9 bytes another 1,048,576: 362 bytes allocated 661 MB in a DOM, and a SAX handler received 1M events per 9 bytes.

## Change

- The reader adds the counts of all such arrays of one input and rejects the input with `out_of_range.408` when the sum exceeds 1,048,576 plus 4 for every byte read so far. The per-array limit is the base, so an array accepted on its own before is still accepted at the start of an input. The check runs once per valueless array, before its start event, with plain `size_t` arithmetic that cannot overflow for a 32-bit `size_t`.
- Containers with a payload type and objects are bounded by the input already and are unchanged. BJData rejects these types.
- `to_ubjson` counts the elements of the typed arrays it writes in one call and writes an array in the unoptimized form (`[#n Z Z ...`) once it would bring the total above 1,048,576, which a reader accepts at any input size. Everything `to_ubjson` writes in 3.13.0 can therefore be read back. BJData and other arrays do not pay for the check.
- Documented in `ubjson.md`, `from_ubjson.md`, `to_ubjson.md`, `exceptions.md` and `untrusted_input.md`.

## Also: an optimized array of no-ops is empty (#6079)

#6079 was merged into this branch. A no-op (`N`) is not a value, so `[$N#n` holds no element whatever count it declares, but the reader passed the declared count on: a SAX handler was told `start_array(n)` and no element followed, and the DOM parser reserved `min(n, 16384)` values (256 KB) for an array that stays empty. Nine bytes (`[$N#l 0x7FFFFFFF`) committed 256 KB, and 2,000 of them (18 KB of input) 512 MB. The reader now announces 0 elements for such an array. A count that does not fit into `std::size_t` is still rejected.

## Measurements (Apple clang -O2, arm64)

Reproducer (K arrays of 1,048,576 nulls): K=40 (362 bytes) before 41,943,040 values, 664 MB, after rejected, 33 MB; K=2 (20 bytes) before 2,097,152 values, 53 MB, after rejected, 33 MB. Accepted valueless arrays cost about 80 bytes of memory per input byte plus the base; the memory of a document as a whole is not bounded by this.

No file of `json_test_data` (846 round trips in all three modes) holds an array of this kind with more than 0.17 values per byte; all of them are read back. The review measured the reader and writer on canada, twitter and a small message: within noise.

## Tests

`unit-ubjson.cpp`: limit, boundary and accounting cases, the writer fallback and round trips, and arrays of no-ops that are reported and stored as empty. Counting events with a SAX handler where possible keeps them cheap (about 22 s under Valgrind).

## Breaking changes

Behaviour changes, no signature change:
- **Reader:** an input with more than 1,048,576 elements in arrays of type `Z`, `T` or `F` at more than 4 per byte is rejected with `out_of_range.408`.
- **Writer:** `to_ubjson` writes an array in the unoptimized form once the total of valueless typed elements exceeds 1,048,576, e.g. 270,000 rows of 100 nulls take 26.8 MB instead of 1.35 MB (up to about 20× larger).
- **No-op arrays (#6079):** `sax_parse` reports `start_array(0)` for `[$N#n` (before: `n`), and `from_ubjson` no longer throws `out_of_range.408` for such an array whose count exceeds the maximum size of the array type, because the array is empty.
