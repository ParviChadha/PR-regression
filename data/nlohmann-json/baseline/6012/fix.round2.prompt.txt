[system]
You write test programs that probe a C++ library for behavioral changes made by one pull request.
Each program is compiled and run twice, once against the library before the change and once after, and the two
outputs are compared. Your job is to produce programs whose output reveals whether the change altered behavior,
including side effects the author did not intend.

Rules for every program:
- It is standalone: one file with its own int main(), compiled as C++17, printing results to stdout.
- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point
  values with an explicit precision. No input, files, network, threads, clocks or randomness.
- Wrap calls that may throw in try/catch and print the exception's type and message, so an exception is an
  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.
- When the diff changes which types or inputs an API accepts or rejects (constraints, overloads, traits,
  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program
  compiles against both versions, prints whether the expression is well-formed, and exercises it when it is.
  Accepting an input is not enough: also use it through every entry point that should follow (const and
  non-const, read, write, insert, erase, lookup, nested use), because a change that admits new inputs can leave
  later code unable to handle them.
- If the changed code is internal (a detail, impl or internal namespace, a trait, a helper), do not name it in the
  program. Reach it through the public API that depends on it, using detection (as above) where needed.
- Use the exact types and values the diff is about (the new trait's argument types, the new overload's
  parameters), not stand-ins.
- Spread the programs over distinct public entry points and overloads, one main idea per program. Do not write
  several programs that only rename a type or change a literal.
- Make the programs differ from each other: different inputs, different entry points, different features.

Rules specific to this library:
- Include the library with #include <nlohmann/json.hpp>. The public API is nlohmann::json (nlohmann::basic_json), nlohmann::ordered_json, json_pointer, json patch/merge_patch and the documented SAX and conversion interfaces. Never use the detail namespace.
- It is a header-only library: nothing to link. Programs are compiled as C++17.
- Print JSON values with dump() (compact) or dump(2). Keys of nlohmann::json objects print in sorted order, so output is deterministic; do not depend on insertion order except with ordered_json.

# Pull request #6012: Restore the two commits of #6005 that the stack merge dropped (fixes the build of develop)

## Description
Fixes the compile error on `develop` (3354436, #6006 and later):

```
include/nlohmann/json.hpp:5550: error: use of undeclared identifier 'null_result'
```

## Cause

#6005 consisted of three commits. When the stack #5997 ← #6004 ← #6005 ← #6006 was restacked for the atomic stack merge, only the last commit of #6005 ("Drop the null_result parameter JSON_IMPLEMENT_OPERATOR no longer uses") was replayed. The two commits it depends on were lost, so `develop` has the parameter removal without the change that made it unused:

- `2ac0851` basic_json, iterators, serializer: remove checks that invariants make dead
- `7196bc5` iter_impl: keep the type-dependent initialization in the constructor

## Change

This PR cherry-picks exactly these two commits (unchanged) onto `develop`. They apply without conflicts.

Checked locally: `make amalgamate` leaves no diff; `unit-comparison`, `unit-allocator`, `unit-iterators1`, `unit-serialization`, `unit-ordered_json` and `unit-json_view` build with clang++ -std=c++11 and pass.

## Breaking changes

No breaking changes: the commits remove internal checks and an unused internal macro parameter.

## Commit message
* basic_json, iterators, serializer: remove checks that invariants make dead

Branch coverage of the test suite and of 24k mutated inputs showed
these conditions as never taken; each is implied by the code around it:

- copy_object_level(): `src_it != src_object.cend()`; dst was built from
  exactly src_object.size() unique keys and src_it advances at most once
  per member
- the general comparison operators (equal_general, less_general,
  three_way_general): the five same-type scalar cases, which the inline
  fast path of every operator handles before calling them (now an
  assert); and the NaN half of compares_unordered() in the mixed-type
  branch, reached only after all six number pairs returned, where only
  a discarded operand is unordered
- serializer, ensure_ascii: the reset of `bytes` under error_handler_t::keep
  and the surrogate-pair escape in the UTF8_ACCEPT case; every
  well-formed multi-byte character is escaped by write_u_escapes() before
  decode() sees it, so decode() only ever accepts DEL here, a single byte
  of which nothing was buffered (now asserts)
- iter_impl(pointer): the if/else chain assigned value-initialized
  iterators to the value-initialized m_it

No change in behaviour: a build that aborts on each removed side passes
the test suite, the fuzz corpora and 23.2M dumps of all 1-, 2- and
boundary 4-byte strings in both ensure_ascii modes.

Signed-off-by: Niels Lohmann <mail@nlohmann.me>

* iter_impl: keep the type-dependent initialization in the constructor

The check is not needed for correctness (m_it is value-initialized), but
without it GCC 13 generates slower iteration loops: a recursive walk over
a parsed document takes 0.5-2.7 % longer (callgrind: +1.9 % instructions
on twitter.json, +0.95 % on canada.json). Clang generates identical code
either way. See the measurements in #6005.

Signed-off-by: Niels Lohmann <mail@nlohmann.me>
