# Pull request #6020: Binary writers: zero only a window ahead of the vector sink's position

## Description
## Summary

`output_vector_sink` (the sink behind `to_cbor(j)`, `to_msgpack(j)`, `to_ubjson(j)`, `to_bjdata(j)`, `to_bon8(j)` and `to_bson(j)` returning a `std::vector`) grew the vector by resizing it to its whole new capacity. `resize()` zeroes the characters it adds, so each doubling zeroed megabytes of a fresh allocation at once. That faults in all the pages and pushes them out of the cache before the writer gets there, so the writer's stores miss again.

The sink now reserves the same capacity as before, but resizes the vector only to 64 KiB (`vector_sink_window`) ahead of the write position, which is still in the cache when the writer's stores come. The vector's capacity and growth stay as they were. The destructor still trims the vector to the bytes written, and `binary_reserve_hint` is unchanged: it is still a lower bound.

## Why

The 3.13.0 writers gained much less on x86 than on Apple M1. For example, `to_cbor` of a number array got 2.4× faster on a Skylake laptop and 4.8× faster on an M1 Max. A/B runs (3.12.0 and develop in one binary, alternating samples, 4 code layouts) found the reason:

- **Not the compiler.** GCC 16 and Clang 23 on a Haswell VPS behave like Apple clang 13 on the Skylake laptop.
- **Not the encoders.** With output reused between repetitions, the Skylake laptop takes 1.8–2.2× as long as the M1, the same as across the whole suite.
- **Fresh output memory.** The rest is page faults, zero-filling and reallocation copies of a 9–80 MB output. That is 30–76 % of the 3.13.0 time on x86 and 13–40 % on the M1. The cost is the same as in 3.12.0; the encoding around it got faster.

This PR removes the part of that cost the sink adds itself: zeroing the whole doubled capacity ahead of the writer.

## Measurements

develop vs this branch, 33 rows (to_cbor/msgpack/ubjson/bjdata/bon8/bson of number arrays and the nativejson documents), geometric mean over 4 layouts, 15 pairs each:

| | Apple M1 Max | Skylake laptop, Apple clang 13 | Haswell VPS, GCC 16 | Haswell VPS, Clang 23 |
|---|---|---|---|---|
| cbor/msgpack, 1M ints | −1.4 … −1.6 % | −10 … −11 % | −13 … −18 % | −11 … −15 % |
| cbor/msgpack, 1M floats | −2.5 % | −13 … −15 % | −18 % | −21 … −22 % |
| ubjson/bjdata/bon8, ints and floats | −1 … −2.5 % | −9 … −17 % | −10 … −22 % | −14 … −26 % |
| small_signed_ints | −1 % | −4.5 % | −5 % | −4.5 % |
| twitter, citm, canada (all formats) | within 0.4 % | within 0.4 % (rerun, 60 pairs) | within 0.4 % | within 0.4 % (rerun, 60 pairs) |

The rows that first read 1–2 % slower on the noisy x86 machines were within 0.4 % in reruns, and their callgrind instruction counts go down (cbor twitter −2.4 %, canada −0.5 %). On the M1 the gain is below 3 %; no row there is slower.

## Tests

`unit-binary_writer_sinks.cpp` gets a test value whose output spans several 64 KiB windows in every format, so the windowed growth is compared against the adapter sink byte for byte. The full suite passes with ASan/UBSan.

## Breaking changes

No breaking changes. The public API, the output bytes and the capacity of the returned vector are unchanged. `vector_sink_window` is a new constant in `nlohmann::detail`.
