# Pull request #5992: json_view: get<T>() of a boolean throws for the exact number types, as basic_json does

## Description
Fixes #5988.

`get<T>()` of a JSON boolean in `basic_json` returns 0/1 for arithmetic types but throws `type_error.302` for exactly `number_integer_t`, `number_unsigned_t` and `number_float_t` (their dedicated `from_json()` overloads go through `get_arithmetic_value()`, which has no boolean case). This has been the behaviour of all 3.x releases and stays unchanged. `json_view::get<T>()` returned 0/1 for every `T`, contradicting its documented parity with `basic_json`.

### Changes

- `detail/view/value.hpp`: a trait `rejects_boolean<T, BasicJsonType>` (true for exactly the three number types of the view's `BasicJsonType`, so custom specializations are followed) selects, by tag dispatch, between 0/1 and the same `type_error.302` the DOM throws, with the view's usual path/bytes decoration. `get_to()` and `value()` follow because they go through `get<T>()`.
- Docs: `basic_json/get.md` gets a note "Booleans as numbers" describing the matrix; `basic_json_view/get.md` names the three exceptions.
- Tests: `unit-conversions1.cpp` pins the DOM matrix (portable types only: `long`/`unsigned long` are `int64_t`/`uint64_t` on some platforms); `unit-json_view.cpp` compares DOM and view (same value or the same exception message) for true/false over 17 arithmetic types, plus `get_to()` and `value()`. The view test fails on develop and passes with the fix.

### Performance

A/B harness (`view_iterate`, Mac instruction counts), develop → this PR: walk 0.997–1.001, items 1.002–1.008, get canada 0.992, lookup twitter 1.001. No row worse than 1 %.

### Public API

No breaking changes for `basic_json`. `json_view` (unreleased) now throws `type_error.302` for `get<std::int64_t>()`, `get<std::uint64_t>()` and `get<double>()` (with the default types) of a boolean, as `basic_json` does.

## Linked issue #5988: get<T>() of a boolean throws for the exact number types but not for other arithmetic types; json_view disagrees with basic_json
### Description

Whether `get<T>()` of a JSON **boolean** yields `0`/`1` or throws depends on which arithmetic `T` is asked for, and `json_view::get<T>()` disagrees with `basic_json::get<T>()` for exactly the types where the DOM throws:

| `T` | `json(true).get<T>()` | `json_document::parse("true").root().get<T>()` |
|---|---|---|
| `int`, `long`, `unsigned`, `short`, `char`, `float`, `long double` | 1 | 1 |
| `long long` / `std::int64_t` (`number_integer_t`), `std::uint64_t` (`number_unsigned_t`), `double` (`number_float_t`) | throws `[json.exception.type_error.302] type must be number, but is boolean` | 1 |

(`get<bool>()` gives `true` in both.) So `get<int>()` and `get<long long>()` of the same value behave differently, and `get<float>()` works while `get<double>()` throws.

**Root cause (DOM).** [from_json.hpp](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/detail/conversions/from_json.hpp) has dedicated overloads for `number_float_t`, `number_unsigned_t` and `number_integer_t` ([#L240-L256](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/detail/conversions/from_json.hpp#L240-L256)) that call `get_arithmetic_value()`, which has no `boolean` case and throws `type_error.302` ([#L194-L199](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/detail/conversions/from_json.hpp#L194-L199)); every other arithmetic type takes the generic overload at [#L611-L625](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/detail/conversions/from_json.hpp#L611-L625), whose comment says *"unlike get_arithmetic_value(), a boolean is accepted here"*.
