# Pull request #6002: UBJSON/BJData/MessagePack reader: reject a container count equal to SIZE_MAX

## Description
## Summary

The UBJSON/BJData reader marks a container whose count is not known by `npos`, which is `SIZE_MAX`. A count of exactly that value was stored unchanged and then treated as "no count", so this BJData input parsed as `[1]`:

```
[ # M ff ff ff ff ff ff ff ff i 01 ]
```

A count of 2^64-2 throws `out_of_range.408` ("excessive array size"), and CBOR already rejects a definite length equal to its unknown-size sentinel. Where `size_t` is 32 bits, the same holds for 'm' and 'L' counts of 2^32-1, in UBJSON too.

The counts of the 'm', 'M' and signed markers now go through `store_ubjson_count()`, which rejects `npos` with "integer value overflow", the message a count beyond `size_t` already gets:

```
[json.exception.out_of_range.408] syntax error while parsing BJData size: integer value overflow
```

One existing expectation changed: an ND-array whose first dimension is 2^64-1 (`vMX` in `unit-bjdata.cpp`) now gets this message on 64-bit platforms too, where it was "excessive ndarray size caused overflow" from the later product check; 32-bit platforms already reported "integer value overflow" for it. The `#if` around that check is gone.

### MessagePack (from review)

Where `size_t` is 32 bits, a MessagePack array 32 or map 32 (`0xDD`/`0xDF`) length of `0xFFFFFFFF` also equals `unknown_size()`. It was passed straight to `start_array()`/`start_object()`, which then skipped their `max_size()` check: the input was still rejected, but with "unexpected end of input", and a custom SAX handler was told the size was unknown. Both now go through the CBOR length check, renamed from `get_cbor_container_size()` to `get_container_size()`, and get the CBOR message:

```
[json.exception.out_of_range.408] syntax error while parsing MessagePack size: excessive array size
```

The remaining 32-bit size slots were checked and need nothing: CBOR's 32-bit lengths already used that check, UBJSON 'l' is signed (at most 2^31-1), BSON has no element counts, and string/binary lengths have no sentinel value.

Tests: `unit-bjdata.cpp` (count equal to `SIZE_MAX` for 'M', and for 'm' and 'L' where `size_t` is 32 bits; 2^64-2 still reports an excessive size), `unit-ubjson.cpp` ('L' = 2^32-1 where `size_t` is 32 bits) and `unit-32bit.cpp` (MessagePack array 32 and map 32 of `0xFFFFFFFF`, next to the CBOR case). Locally the msgpack, cbor, ubjson, bjdata and regression2 tests pass on 64-bit; the 32-bit cases only run in CI's 32-bit job.

Found by a review of runtime checks in the binary readers (the `first != npos` guards next to the count are what made the sentinel collision visible).

## Breaking changes

No breaking changes to the API. One crafted BJData/UBJSON input that was accepted as `[1]` now throws `out_of_range.408`, as a count of 2^64-2 already did; on 32-bit platforms a MessagePack array/map 32 of `0xFFFFFFFF` now throws `out_of_range.408` instead of `parse_error.110`. No valid document is affected (no container can hold `SIZE_MAX` elements).
