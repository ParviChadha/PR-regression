# Pull request #6117: Force inlining of the serializer helpers only in optimized builds

## Description
Fixes #6116.

## Problem

The seven serializer helpers marked `JSON_HEDLEY_ALWAYS_INLINE` (#5878, #5883) are inlined at `-O0` too, and GCC and Clang give every inlined copy its own stack slots there. The recursive frame of `serializer::dump_container()` grew from 480 bytes in 3.12.0 to 2,304 bytes (Clang 21) or 2,048 bytes (GCC 16). With the default `JSON_RECURSION_DEPTH_LIMIT` of 128, `dump()` of a deep value therefore needed 288 KiB of stack in an unoptimized build, and a 277-byte document nested 138 levels crashed `dump()` in a musl thread with the default 128 KiB stack (GCC 14 `-O0`, Alpine), where 3.12.0 worked.

## Change

- `macro_scope.hpp` defines `JSON_INTERNAL_SERIALIZER_INLINE`: `JSON_HEDLEY_ALWAYS_INLINE` when `__OPTIMIZE__` (GCC and Clang at every `-O` level above `-O0`, including `-Og` and `-Os`) or `_MSC_VER` is defined, plain `inline` otherwise. MSVC keeps `__forceinline`, as `/Ob0` debug builds do not expand it anyway, so there are no new C4714 warnings. `macro_unscope.hpp` undefines it.
- The seven helpers use it: `dump_element`, `emit_pending`, `reserve_string_buffer`, `put_indent`, `put_literal_indent`, `put_short_literal_indent`, `put_literal`.
- `json_recursion_depth_limit.md` and `untrusted_input.md`: the `dump` row of the `-O0` table, the cost per level, the "which limit to choose" table and the summary table are updated. At `-O0`, copying and conversion to another `basic_json` type are now the most demanding operations (224 KiB at the default limit instead of 288 KiB). The other rows are unchanged; re-measuring them on develop reproduced the published `dump` row exactly.

## Measurements (macOS, arm64)

Smallest stack for `dump()`/`dump(4)` of nested arrays and objects at depth limit + 10, `-O0`, C++20, Clang 21 / GCC 16:

| | limit 16 | limit 32 | limit 64 | limit 128 | limit 254 |
|---|---:|---:|---:|---:|---:|
| before | 48 / 32 | 80 / 64 | 144 / 128 | 288 / 256 | 576 / 512 |
| after | 16 / 16 | 16 / 16 | 32 / 32 | 48 / 48 | 96 / 96 |

At `-O2 -DNDEBUG`, the disassembly of a TU that calls `dump()`, `dump(4)`, `diff()` and copies is byte-identical before and after, with Clang 21 and with GCC 16. So optimized builds do not change at all.

## Tests

No unit test: a stack-size test is not portable (pthreads only; sanitizer and coverage builds have much larger frames). Passing at `-O0` and `-O2` with ASan and UBSan in C++11: `unit-serialization` (162,060 assertions), `unit-recursion_depth_limit`, `unit-inspection`, `unit-testsuites`. `unit-serialization` also passes with GCC 16 at `-O0`. The macro does not leak from `json.hpp` or `json_view.hpp`. clang-tidy (CI configuration) is clean.

## Breaking changes

None. No API or behaviour change; only the inlining of private serializer helpers in unoptimized builds differs.

## Linked issue #6116: dump(): the recursive frame grew from 480 to 2304 bytes in unoptimized builds, so 128 levels need 288 KiB of stack
### Description

Since #6081, `dump()` and the other value walks recurse at most `JSON_RECURSION_DEPTH_LIMIT` levels (128 by default) and continue with an explicit stack. The stack that these levels need is documented ([`JSON_RECURSION_DEPTH_LIMIT`, "Stack needed"](https://json.nlohmann.me/api/macros/json_recursion_depth_limit/#stack-needed) and [Nesting depth](https://json.nlohmann.me/features/parsing/untrusted_input/#nesting-depth)):

> The default of `128` levels is tuned for threads with ordinary stacks of a few hundred kilobytes or more. Set a lower limit if your threads have small stacks (RTOS tasks, fibers, threads of the musl C library, which has a default stack of 128 KiB) [...]

So this is not a bug: a crash on a 128 KiB thread at `-O0` is a documented configuration that needs a lower limit. But the main reason for the 288 KiB is avoidable. `dump()` is by far the most demanding operation at `-O0` (288 KiB; copy needs 160 to 208 KiB, everything else 64 KiB or less), and its cost per level comes almost entirely from one stack frame that grew sixfold since 3.12.0:

| recursive frame, `-O0` (`-fstack-usage`) | 3.12.0 | develop |
|---|---:|---:|
| Apple clang 21, `serializer::dump` / `dump_container` | 480 B | 2304 B |
| GCC 16.2 (Homebrew, macOS), `dump_container` | | 2048 B |
