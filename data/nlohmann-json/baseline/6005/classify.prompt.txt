# Pull request #6005: basic_json, iterators, serializer: remove checks that invariants make dead

## Description
## Summary

Removes runtime checks in `basic_json` and the serializer that the surrounding code already guarantees, so they can never fire. Each condition was shown dead by branch coverage and by a build that aborts on the removed side (see below).

This PR is stacked on #5997 (which removed the surrogate-pair branch of the serializer's `ensure_ascii` path) and on the lexer/parser PR of this series.

- `json.hpp`, `copy_object_level()`: `src_it != src_object.cend()`. `dst` was built from exactly `src_object.size()` unique keys, and `src_it` advances at most once per member of `dst`.
- `json.hpp`, the general comparison operators (`equal_general`, `less_general`, `three_way_general`, built by `JSON_IMPLEMENT_OPERATOR`): the five same-type scalar cases (null, boolean, integer, unsigned, float). Every operator runs `JSON_IMPLEMENT_SCALAR_FAST` first, which returns for exactly these cases, and `equal_structured()` only calls `equal_general()` after `equal_leaf()` declined, which it never does for them. The cases now assert and return the unordered result. In the same macro, `compares_unordered(lhs, rhs)` in the mixed-type branch is reduced to its discarded half: it is reached only after all six number-pair branches returned, and a float with a non-number operand is never "unordered" there.
- `serializer.hpp`, `ensure_ascii`: the reset of `bytes` under `error_handler_t::keep` in the `UTF8_ACCEPT` case. Every well-formed multi-byte character is escaped by `write_u_escapes()` before `decode()` sees it, so `decode()` only ever accepts DEL (0x7F) here, a single byte of which nothing was buffered. Both facts are now asserts.
- ~~`iter_impl.hpp`, `iter_impl(pointer)`: the if/else chain assigned value-initialized iterators to the value-initialized `m_it`.~~ **Dropped** (commit 7196bc5b22): the chain is dead for correctness, but removing it made iteration slower with GCC 13. A recursive range-for over a parsed document took 0.5–2.7 % longer on x86-64; callgrind counted +1.9 % instructions on twitter.json and +0.95 % on canada.json. Clang generates identical code either way. The constructor is back as it was, with a comment saying why it stays. Measurements are in the performance comment below.
- `JSON_IMPLEMENT_OPERATOR` loses its `null_result` parameter, which only the removed scalar cases used (review follow-up). `JSON_IMPLEMENT_SCALAR_CASES` keeps it, since `JSON_IMPLEMENT_SCALAR_FAST` still uses it.

Net: 23 insertions, 22 deletions in `include/` (including the comment that keeps `iter_impl` as it was); no test changes.

## How the checks were found and verified

1. Branch coverage of the whole test suite (clang `-fprofile-instr-generate`) plus 24,380 mutated JSON and binary inputs through the `tests/src/fuzzer-*.cpp` drivers listed the branch sides never taken in `include/nlohmann/`.
2. Each candidate was read for the invariant that makes it dead and the line that establishes it (the commit message names them).
3. A copy of the tree with `abort()` on the supposedly dead side of every check was run through the full test suite under ASan/UBSan, the fuzz corpora and dedicated drivers: no trap fired. (One claim was disproved this way and is not part of these PRs.)
4. With the checks removed, the full test suite passes under ASan/UBSan, and a wide translation unit compiles without a new warning under the CI clang flag set (C++11 and C++17, with and without `JSON_DIAGNOSTICS` / `JSON_DIAGNOSTIC_POSITIONS`).

The full list of findings, including checks that are dead only in the shipped configurations and were left in place, is in a separate report; this PR covers the high-confidence items of its area only.

In addition, a serializer driver dumped all 1-byte, 2-byte and boundary 4-byte strings (23.2M dumps) in both `ensure_ascii` modes with every error handler against the trap build.
