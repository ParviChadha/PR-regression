# Pull request #6076: Make unflatten() linear in the length of the keys

## Description
`unflatten()` takes quadratic time in the number of reference tokens of one key on current `develop` (3.13.0 work in progress; 3.12.0 is linear). An object with one key of 100,000 `/0` tokens (200 KB) takes 2.4 s; 3.12.0 needs 5 ms. The time quadruples with each doubling of the key. An attacker who controls one key of an object passed to `unflatten()` can make the process busy for minutes with a few megabytes of input. `unflatten.md` promises "Linear in the size of the JSON value".

## Cause

3.13.0 decides in a first pass which prefixes of the keys denote arrays (those that have a reference token `0` among their children), so that the result no longer depends on the order of the keys, and looks the prefixes up again in the second pass. A prefix was identified by hashing it and by comparing it byte by byte with the set entry, from its beginning, so a key with n tokens cost n²/2 bytes. For `ordered_json` (and any unsorted object type) the shortcut for keys that share a beginning with the previous key does not help: four keys were enough to be quadratic.

## Change

- Prefixes shorter than 64 bytes stay in the hash table and are compared as before (a bounded number of bytes).
- Longer prefixes are kept in a tree whose nodes are looked up by their parent and the text of one token. The node of a prefix is found by walking the tokens of the key from the root, so all prefixes of a key together cost one pass over the key and no prefix is compared as a whole. The nodes along the key walked last are kept, so keys with a common beginning do not walk it again. No recursion.
- The hash function is seeded with a value derived from the address of a local variable (ASLR changes it between processes). With the previous fixed constants, crafted keys could be made to collide: 20,000 keys of 18 bytes with equal hash took 0.5 s instead of 7 ms. Where addresses are not randomized, or if the seed is known, k short prefixes (< 64 bytes) can still collide and cost k²/2 comparisons of fewer than 64 bytes. Results never depend on the seed.
- The array/object decision and the independence from the key order are unchanged. Only private helpers of `detail::json_pointer` changed.

## Linked issue #6105: ordered_json::unflatten() silently overwrites a nested value when a key is a prefix of an earlier key
### Description

`unflatten()` must reject keys whose JSON pointers overlap. The [`unflatten()` documentation](https://json.nlohmann.me/api/basic_json/unflatten/#exceptions) says:

> Throws `type_error.313` if a key (JSON pointer) leads to a conflicting nesting

and [`type_error.313`](https://json.nlohmann.me/home/exceptions/#jsonexceptiontype_error313) says "The JSON Pointers must not overlap, because then the resulting value would not be well-defined."

`json` keeps this promise, `ordered_json` does not. For `{"/a/b":2,"/a":1}`, `json` throws `type_error.313`, but `ordered_json` returns `{"a":1}`: the member `b` is dropped without an error. The same happens for an array element (`{"/a/0/b":1,"/a/0":2}` gives `{"a":[2]}`) and for the root (`{"/x":1,"":2}` gives `2`).

Cause: the conflict check only happens while walking the reference tokens of a key: a primitive value in the middle of a path throws (the `default:` branch of the `switch` in `unflatten()`). The final assignment has no check:

[`include/nlohmann/detail/json_pointer.hpp#L2241`](https://github.com/nlohmann/json/blob/5bad6c518bf6663b69f505511a19c98c91f77c3a/include/nlohmann/detail/json_pointer.hpp#L2241)

```cpp
                values.push_back(current);
                ends.push_back(end);
                pos = end;
            }

            *current = element.second;
```

`std::map` visits `"/a"` before `"/a/b"`, so for `json` the shorter key always comes first, it stores the primitive, and the longer key then hits the primitive and throws. An insertion-ordered object can present the longer key first. The walk for `"/a/b"` creates the object `a`, and the assignment for `"/a"` then replaces that object with `1`.

The 3.13.0 notes for `unflatten()` say that the array/object decision "does not depend on the order in which the flattened object is iterated". This bug is the remaining order dependence.
