Each program is compiled and run twice, once against the library before the change and once after, and the two
outputs are compared. Your job is to produce programs whose output reveals whether the change altered behavior,
including side effects the author did not intend.

Rules for every program:
- It is standalone: one file with its own int main(), compiled as C++17, printing results to stdout.
- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point
  values with an explicit precision. No input, files, network, threads, clocks or randomness.
- Wrap calls that may throw in try/catch and print the exception's type and message, so an exception is an
  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.
- When the diff changes which types or inputs an API accepts or rejects (constraints, overloads, traits,
  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program
  compiles against both versions, prints whether the expression is well-formed, and exercises it when it is.
  Accepting an input is not enough: also use it through every entry point that should follow (const and
  non-const, read, write, insert, erase, lookup, nested use), because a change that admits new inputs can leave
  later code unable to handle them.
- If the changed code is internal (a detail, impl or internal namespace, a trait, a helper), do not name it in the
  program. Reach it through the public API that depends on it, using detection (as above) where needed.
- Use the exact types and values the diff is about (the new trait's argument types, the new overload's
  parameters), not stand-ins.
- Spread the programs over distinct public entry points and overloads, one main idea per program. Do not write

# Pull request #5915: json_view: fewer allocations when parsing small documents

## Description
1. **Size the buffer of decoded strings on its first growth from the input.** A quarter of the input plus 16 bytes, capped at 4 KiB, instead of 272 bytes: a document with escapes no longer grows it twice, with a zero-filled copy each time. The cap keeps a large document with one escape from zero-filling a large buffer.
2. **Allocate the node index of documents with an estimate of up to 1024 nodes (was 256) together with the header.** One allocation less. The limit is a named constant, `document_data::max_inline_nodes`.

## Numbers

`compare.py --download --rounds 30`, Apple M1 Max, clang 21, develop vs this PR, each unaligned twice and once aligned (reference engines moved by a median of 1.000 in the aligned run). Ratio = this PR / develop, aligned and the two unaligned runs:

| row (2.5 KB minified tweet with escapes) | ratio |
|---|---|
| parse | 0.959, 0.964, 0.950 |
| traverse | 0.967, 0.981, 0.963 |
| select | 0.969, 0.975, 0.955 |
| parse+dump | 0.972, 0.974, 0.960 |
| `rpc` parse / dump (not affected) | 1.006, 1.007, 0.993 / 1.024, 1.005, 1.011 |

Fresh parse of the tweet: 993 to 958 ns (best of three). It stays behind yyjson (about 1.11x before, about 1.07x after). No `json_view` row is consistently slower in all three runs; a few large-document rows moved by 2-4 % in one run and not in the aligned run, on code this PR does not touch.

Fresh parse and `memory_usage()` of dense numeric arrays (more nodes per byte than the estimate expects):

| document | parse | memory_usage() |
|---|---|---|
| 1 KB, 500 numbers | 2047 to 1863 ns | 11,310 to 15,566 B |
| 4 KB, 2000 numbers | 7907 to 7225 ns | 41,310 to 57,566 B |

### Trade-off

When the estimate is too low (dense numbers), the node block that was allocated with the header stays unused: at most 16 KiB instead of 4 KiB. Documents whose estimate fits keep the same memory. `shrink_to_fit()` cannot release a node index that lives in the header allocation; it was already documented as non-binding, and the page now says which part cannot be released.

## Validation

- New "block sizes" test section: escaping and dense documents of 1 to 5000 elements around the 256 and 1024 node points (also pretty-printed, and after `shrink_to_fit()`), and a 100k-node document with one escape.
- All six `json_view` unit test files with ASan/UBSan, in C++11 and C++17.
- `single_include` is a fresh `make amalgamate` (`json.hpp` is unchanged).

## Public API

No breaking changes. `memory_usage()` can report more memory for dense small documents, as described above; no signature or documented guarantee changes.
