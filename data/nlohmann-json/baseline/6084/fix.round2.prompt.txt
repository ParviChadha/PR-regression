# Pull request #6084: Reject integer tokens in float nodes of fully checked json_view images

## Description
# Reject integer tokens in float nodes of images loaded with image_check::full

`json_document::load(image, image_check::full)` accepted a float node whose token is an integer literal that fits 64 bits. Example: save the image of `18446744073709551616` (2^64, which the parser stores as a float), change the second digit to `0` in the image, and `load()` succeeds. The loaded node is a float (`is_number_unsigned()` is `false`, `dump()` prints `1.0446744073709552e+19`), while parsing the same text gives an unsigned integer (`10446744073709551616`). The documentation promises that a fully checked image is as safe and as faithful as a freshly parsed document, so `full` must reject this with `parse_error.116`. There is no memory-safety effect. `json_view` is new in 3.13.0, so nothing released is affected.

## Cause

`check_float_ranges` scanned the token and checked its digit layout and finiteness, but never required it to be something the parser stores as a float. A float node is legitimate only for a token with a fraction or an exponent, or for an integer token that does not fit 64 bits.

## Change

- New `integer_token_fits` in `detail/view/image.hpp`: at most 20 digits, 20 digits not above `18446744073709551615`, a negative one not below `-9223372036854775808` (the same bounds that `check_integer` applies to integer nodes). `check_float_ranges` rejects a float node whose token has no fraction and no exponent and fits. Tokens in the plain `digits.digits` layout (all of canada.json) never reach this branch.
- Docs: `api/basic_json_document/load.md` (`image_check::full`) now says that the token must also have the type the parser gives it. `features/json_view/images.md` needs no change ("exactly as safe to read and serialize as a freshly parsed document" is true with this fix).
- `single_include/nlohmann/json_view.hpp` regenerated.

## Tests

`unit-json_view_image.cpp`, section "float tokens: an integer token is a float node only if it does not fit 64 bits". For five float-valued integer tokens (2^64, -2^63-1, 10^20, -2^64, a 30-digit number) it replaces every digit (not the sign) by every digit, loads with `image_check::full`, and compares with what the parser does for the changed text: accepted and dumped like `json::parse` if the parser stores a float, `parse_error.116` otherwise (this covers both boundaries). On develop the section fails with 176 failed checks (the changed tokens that fit are accepted); with the change it passes (64002 assertions of the file, ASan/UBSan clean). The existing fuzzer cannot see this: it compares `json::parse(dump())` with `materialize()`, and both give the rounded value.

## Differential check

A harness (385182 tokens, for `json` and `ordered_json` documents) takes a number token, forces a float node over it in a saved image (digit layout of the token and the "many" layout), and compares `load(..., image_check::full)` with what `json::parse` makes of the token: accepted and dumped identically if the parser gives a float, rejected otherwise. It covers fixed boundary tokens, every single-digit mutation of the 2^64-1, 2^63, 2^63-1, 10^19 and 10^20-1 literals with both signs and suffixes (`0`, `.0`, `e0`, `E-1`), 200000 random tokens of 1-24 digits with fractions and exponents, and edited documents (including NaN and infinity). Develop: 298k failures; with the change: 0 failures. `integer_token_fits` decides on the first digit where it can (a 20-digit token needs the string comparison only if it starts with `1`, a negative 19-digit one only if it starts with `9`); the harness was re-run after that.

## Measurements

`json_document::load(image, image_check::full)` of the image of canada.json (4.9 MB, float-heavy; best of 40, clang -O2, Apple silicon, three alternating runs): develop 1.497, 1.514, 1.560 ms; this PR 1.477, 1.497, 1.496 ms (no difference). canada's tokens take the plain-layout fast path, which is unchanged.
