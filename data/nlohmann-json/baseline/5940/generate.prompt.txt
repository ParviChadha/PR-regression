# Pull request #5940: Strong exception guarantee for operator[](json_pointer)

## Description
Stacked on #5358 (its two commits are part of this diff until it merges; then this PR shrinks to the last three commits). Draft until then.

## What
The non-const `operator[](json_pointer)` now has the **strong exception guarantee**: if resolving the pointer throws (`out_of_range`, `bad_alloc`, `length_error` while padding an array, ...), the value is unchanged. Previously, values created for earlier reference tokens stayed behind. Found in the compliance review of JSON Pointer (RFC 6901).

- Rollback via a small RAII guard (no try/catch, so it also works with `JSON_NOEXCEPTION`); it reverts by iterator, so it does not allocate or convert keys.
- `get_unchecked` is a non-inserting walk; creation moved to a never-inlined `get_unchecked_create`, which keeps the hot read path faster than before.
- Object types whose lookup and `emplace()` disagree (copied `fifo_map`) no longer hit an assert/crash; such pointers throw `out_of_range.404` and leave the value unchanged.
- Creating values no longer needs `string_t::begin()` (compiles with the alternative string type of the tests).
- Documentation of `operator[]` states the guarantee and the requirement for custom template parameters.

## Performance

## Breaking changes
No breaking changes to the public API. Behavioural change: a failing `operator[](json_pointer)` now leaves the value untouched instead of leaving partially created values (an exception-safety improvement, was undocumented before).

## Commit message
* Keep the value unchanged when operator[] with a JSON pointer throws

The non-const operator[](json_pointer) is documented with strong exception
safety, but get_unchecked created intermediate values while walking the
pointer and kept them when a later reference token failed, e.g.
json j; j["/a/99999999999999999999999"_json_pointer] threw 404 and left
{"a":[]}; padding an existing array or appending with "-" behaved alike,
and so did std::length_error/std::bad_alloc from a huge index.

get_unchecked now only walks existing values up to the last reference
token. The last token's key insertion or array growth is strongly
exception safe by itself. Any other change goes through
get_unchecked_create, which records the one change it makes to an existing
value (null converted, key inserted, array grown) in a RAII guard and
reverts it if a later step throws; everything else it creates lies below
that change. The guard needs no try/catch, so JSON_NOEXCEPTION builds are
unaffected. Successful calls create the same values as before.

Docs: state the guarantee in the exceptions list and version history of
operator[], fix the complexity of the pointer overloads of operator[] and
at, and warn that padding arrays up to an untrusted index allocates memory
proportional to the index (operator[].md, untrusted_input.md).
