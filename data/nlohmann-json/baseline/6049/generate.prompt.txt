# Pull request #6049: json_view: keep tokens without an integer digit out of the float batch

## Description
## Problem

OSS-Fuzz issue 583898810 (`json_view_image_fuzzer`, regressed with #5908): an image loaded with `image_check::bounds` makes `dump()` fail the assertion `digits != 0 && digits < 100000000000000000u` in `write_decimal()`.

The image's float node records no digit before the point and 17 after it, which no JSON number has. `convert_ahead()` only required at least 8 fraction digits, so it batched the token with q = -17. `locate_token()` then read `fives[17]` past the 17 entries of its table. What it read depends on the binary's memory layout: in the fuzzer's x86-64 build, the digits came out as 10^17 + 64 (18 digits), and `write_shortest()` passed 18 digits on to `write_decimal()`.

## Change

- The batch takes tokens with 8 to 16 fraction digits (`frac_digits - 8u <= 8u` instead of `frac_digits >= 8`). Every valid token of 16 or 17 digits has at least one digit before the point, so the batch handles the same tokens of valid documents as before; the comparison costs the same.
- `locate_token()`'s documentation states its range as -16 <= q <= -1, matching its table.
- A section in `unit-json_view_image.cpp` with a crafted token of this layout and the OSS-Fuzz input itself. Without the fix, it fails on arm64 with a bounds-checked libc++ (`_LIBCPP_HARDENING_MODE_DEBUG`) and on x86-64 with the `write_decimal()` assertion. No CI job checks container bounds, so the crafted case alone would not fail there.

Random damage to the testcase and to near-10^17 tokens (about 58M images, x86-64) found no other crash with the fix.

## Tests run locally

- the OSS-Fuzz testcase through `fuzzer-json_view_image.cpp` on x86-64: assertion before, passes after
- all 22 json_view test targets (CMake Debug, arm64): pass
- not run: the rest of the test suite and a benchmark (no measurable change expected)

## Breaking changes

No breaking changes: the public API is untouched.
