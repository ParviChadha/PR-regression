# Pull request #5991: parse(): propagate std::bad_alloc instead of crashing on a half-constructed member

## Description
Fixes #5985.

When an allocation failed while `json::parse()` built an object or array member, the result was destroyed with a member whose type said *object*/*array* but whose pointer was null, so the destructor dereferenced it instead of the `std::bad_alloc` reaching the caller. Introduced by #5882 (not in any release).

### Cause and fix

`json_sax_dom_parser::set_member()` placement-news the new value over the null member it inserted for the key. `basic_json(value_t)` writes `m_type` before the allocation of `m_value`, so a throwing allocation left the member half-overwritten. Now a value whose construction can throw (a string, a binary value or a container) is created in a local first and placement-new'd into the member by move (the move constructor is `noexcept`), so a failed allocation never touches the member. A value that is nothrow-constructible (null, boolean, numbers) is still constructed in place, as before, so it pays no extra move; the choice is made at compile time with `std::is_nothrow_constructible`. This also covers `ordered_json`, `JSON_DIAGNOSTICS` and `sax_parse()` with `detail::json_sax_dom_parser` into an existing value (same code). The callback parser and the binary parsers assign a temporary and were not affected.

### Tests

`tests/src/unit-allocator.cpp`: "parse() survives a failing allocation at every point (#5985)" fails allocation k = 1, 2, … with a counting allocator (checks for a clean `std::bad_alloc` and no leak) for `json`, `ordered_json`, the callback parser (keep-all and filtering) and `sax_parse()` into an existing value. On develop it crashes under UBSan (`json.hpp:912: reference binding to null pointer`); with the fix it passes, also with `JSON_DIAGNOSTICS=1`. The issue's reproducer now runs to `no throw at k=14: done`. Full `ctest` with ASan+UBSan: 188/188.

### Performance

The alternative (setting `m_type` after the allocation in `data(value_t)`) was prototyped too; both were measured against develop with an A/B harness (Mac instruction counts, DOM parse, `json` and `ordered_json`). The chosen fix is at or below develop on all large inputs (twitter 0.996, citm 0.999, canada 0.999, update-center 0.993–0.999, random 0.994–0.996); the alternative was up to +0.8 %. Small inputs (< 1e8 instructions) stay within their ±2 % noise.

These numbers were measured before scalars went back to in-place construction (review follow-up, 4809610d60). That change only removes work from the scalar path, and it has not been re-measured.

### Public API

No breaking changes.

## Linked issue #5985: parse() crashes in the destructor instead of propagating std::bad_alloc (the DOM parser leaves a half-constructed member)
### Description

When an allocation fails while `json::parse()` builds an object or array member, the result is destroyed with a member whose type says *object*, *array* or *string* but whose pointer is null. The destructor then dereferences that null pointer: UBSan reports `reference binding to null pointer`, a debug build fails `assert_invariant()`, a release build segfaults. The `std::bad_alloc` never reaches the caller, although [`parse()` documents the strong guarantee](https://json.nlohmann.me/api/basic_json/parse/#exception-safety).

**Root cause.** The DOM SAX parser constructs a new member *in place* over the existing null member it inserted for the key ([json_sax.hpp#L1300-L1313](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/detail/input/json_sax.hpp#L1300-L1313), the same code in `json_sax_dom_callback_parser`):

```cpp
if (JSON_HEDLEY_LIKELY(member.is_null()))
{
    // a new member is null and holds nothing: construct the value
    // over it instead of destroying and swapping
    ::new (static_cast<void*>(&member)) BasicJsonType(std::forward<Value>(v));
}
```

`basic_json(value_t)` initialises `data::m_type` before `data::m_value` ([json.hpp#L6216-L6219](https://github.com/nlohmann/json/blob/ddc34f546a652cd098dd78225d80f1909b921871/include/nlohmann/json.hpp#L6216-L6219)), and `json_value(value_t)` / `json_value(string_t&&)` allocate. When that allocation throws, the constructor never completes, so no destructor runs for it, but the placement new has already written `m_type = object` (or array/string) into the member's storage, while the union still holds the null member's zero pointer.
