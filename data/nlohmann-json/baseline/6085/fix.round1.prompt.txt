You write test programs that probe a C++ library for behavioral changes made by one pull request.
Each program is compiled and run twice, once against the library before the change and once after, and the two
outputs are compared. Your job is to produce programs whose output reveals whether the change altered behavior,
including side effects the author did not intend.

Rules for every program:
- It is standalone: one file with its own int main(), compiled as C++17, printing results to stdout.
- Use only the library's documented public API. Never include internal headers or use detail/impl namespaces,
  private members or undocumented macros.
- Do not judge results (no assert, no expected-value comparisons): just print what the library returns. Print
  enough to make differences visible, one fact per line.
- Output must be deterministic. Never print pointers or addresses, uninitialized data, the order of
  hash-based containers, timings, thread ids, random values, file paths or environment data. Print floating point
  values with an explicit precision. No input, files, network, threads, clocks or randomness.
- Wrap calls that may throw in try/catch and print the exception's type and message, so an exception is an
  observable result. Do not crash on purpose.
- Aim at the code the diff changes. Prefer calls that compile against both the old and the new library; one or two
  programs may use an API the PR adds. Cover ordinary inputs and edge cases (empty, minimum and maximum values,
  boundaries, special values, nesting, unusual types) and also neighbouring behavior the change could disturb.
- When the diff changes which types or inputs an API accepts or rejects (constraints, overloads, traits,
  conversions), test it with the detection idiom (std::void_t or requires) and `if constexpr`, so the program
  compiles against both versions, prints whether the expression is well-formed, and exercises it when it is.
  Accepting an input is not enough: also use it through every entry point that should follow (const and
  non-const, read, write, insert, erase, lookup, nested use), because a change that admits new inputs can leave
  later code unable to handle them.
- If the changed code is internal (a detail, impl or internal namespace, a trait, a helper), do not name it in the
  program. Reach it through the public API that depends on it, using detection (as above) where needed.
- Use the exact types and values the diff is about (the new trait's argument types, the new overload's
  parameters), not stand-ins.
- Spread the programs over distinct public entry points and overloads, one main idea per program. Do not write
  several programs that only rename a type or change a literal.
- Make the programs differ from each other: different inputs, different entry points, different features.

# Pull request #6085: Do not compare an edited NaN equal to itself in json_view

## Description
Stacked on #6084 (merge that first).

# Do not compare an edited NaN equal to itself in json_view

`operator==` of two views returned `true` for a NaN that an edit wrote (`set()`, `push_back()`, `insert()`): `v[0] == v[0]`, `root == root` and `root == other_root` were all `true`, while `json(NaN) == json(NaN)` and `view == json` are `false`. `a == b` and `a == b.materialize()` therefore disagreed for the same document. This contradicts the documented rule that views compare as `materialize()` would. A NaN can only enter a document through an edit (parsed text cannot hold one), and `json_view` is new in 3.13.0, so nothing released is affected.

## Cause

Two float nodes with equal tokens were taken as equal without reading the value, and an edit stores a NaN as the token text `nan`. In addition, `certainly_equal` returned `true` for the same node of the same document, which is wrong for a NaN and for any array or object that contains one.

## Change

- The equal-token shortcut excludes the edited `nan` token. Edited floats are recorded without a digit layout (`extra == 0xFFFF`), which identifies the token; the check runs only for editable documents (a read-only document cannot hold a NaN, so equal tokens are an equal value there).
- The same-node shortcut is kept for read-only documents and for editable documents that were never edited (no edit storage yet); a document with edits is walked.
- Docs: `basic_json_view/operator_eq.md` says that a NaN written by an edit, and a view of anything containing one, is not equal to itself.
- Infinities, which compare equal as in `basic_json`, are unchanged.

## Tests

`unit-json_view_edit_values.cpp`, section "a NaN written by an edit is not equal to itself". It fails on develop (7 failed checks: `d.root() == d.root()`, `d.root()[0] == d.root()[0]`, `d.root() == other.root()`, ...) and passes with the change. A check for a never-edited editable document (`root == root` stays true) is included. Also run under ASan/UBSan together with `unit-json_view_compare` and `unit-json_view_compare_values`.

## Measurements

`view == view` of two separately parsed, equal documents, clang -O2, Apple silicon, `/usr/bin/time -l`, 200 compares per run, five runs each, parse time included (about 194M instructions for canada, 136M citm, 57M twitter). The float comparison is dispatched on the document mode with a tag (as `scalar_values_only` is), so the read-only walk is the code it was before. Instructions in millions (median), then cycles (median):

| input / case | instr. develop | instr. this PR | cycles develop | cycles this PR |
|---|---|---|---|---|
| canada, read-only | 3112.6 | 3112.4 (+-0 %) | 521.4 | 518.9 (noise) |
| canada, editable == editable | 3357.7 | 3425.3 (+2.0 %) | 534.3 | 540.9 (within noise, runs spread 526-543 and 530-565) |

The editable overhead is one comparison per equal float, which the NaN check needs.

A comparison of a view with itself in an editable document that has edits is now linear instead of constant time (canada about 16M instructions, citm 4.3M, twitter 7.4M per compare); never-edited and read-only documents keep the constant-time shortcut.

## Breaking changes

None. `json_view` has not been released; for released API there is no change.

the same node was equal to itself. An edit writes a NaN as the token

- gregmarr: Why not check the other side?  Is there a guarantee that if one is edited and one is not, the edited one is side a?
- nlohmann: No guarantee is needed: checking either side gives the same answer here. `na == nb` is the same node, and documents have distinct nodes, so `a.document()` and `b.document()` are the same document with the same `edits`. If `ViewA` is the read-only side, that document has no edits: a view converts only from read-only to editable (`is_widening_mode`), and `json_view v = editable_view;` does not compile, so an edited document never has a read-only view.

The same holds in `same_float()` and `floats_equal()`: the NaN test runs only after the two tokens and their `extra` compared equal, so a's token is `nan` exactly when b's is, and a read-only side never holds one. I checked it on this head: an edited NaN compares unequal to itself (`e0 == e0`, `e == e`, `e[0] == e[0]` are all false), and comparisons between read-only and editable views of an unedited value still give `true` in both orders.
